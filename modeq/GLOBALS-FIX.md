## 誤りの機構

$gp 形成は `lui $gp, 0x8023` ＋ `addiu $gp, $gp, 0xDBC0`。addiu の即値 0xDBC0 は
符号拡張で **−0x2440** だから $gp = 0x80230000 − 0x2440 = **0x8022DBC0**。
前任は lui/addiu の半分同士を OR して 0x8023DBC0 と読んだ（0x80230000 | 0xDBC0）。
capstone の表示も `addiu $gp, $gp, -0x2440` で、符号付きであることは表示上も明白。
旧アドレス 0x80237050 の中身が健全状態でも定数 0x2b75aac9 だった実機観測、
絶対アドレス由来の ctx アンカ（0x80253308）だけが実機で正しかったことと完全に整合する。

## 裏取り（独立経路を複数通した）

1. **$gp 形成サイト census（stream 全域）**: `lui $gp` は2箇所のみ
   （VA 0xA0108584、0xA01201B0）、どちらも lui 0x8023 / addiu −0x2440 で値一致。
   `addu $gp,$gp,$t9`（_gp_disp 方式）は全域に0件＝相対補正は存在しない。
2. **カードタスク入口トランポリン @0xA01201B0**: `lui $gp / addiu $gp,-0x2440` の
   直後に `jalr` でモジュールへ入る。カードモジュール（submit を含む）が
   この $gp で走ることの文脈証拠として最も強い。
3. **submit 本体の実読 @0xA0121700**: 先頭 `lw $v0,-0x6B70($gp)` → 直後に
   `lw $v0,0x118($v0); andi 2`（ゲート）＝ state-ptr は −0x6B70 のグローバルで確定。
   ゲート通過後 `lw $a0,-0x6BB4($gp); jal alloc` ＝ pool-ptr は −0x6BB4 で、
   submit 自身がジョブ記述子の alloc に使う（ハンドラの流用前提どおり）。
4. **使用 census**: −0x6B70 の lw はカードモジュール全域に約120件
   （ステートマシン／コールバック群を含む）、−0x6BB4 の lw は約250件で
   ほぼ全て `lw $a0` ＋ jal alloc/free の組。単一の共有グローバルであることと整合。
5. **ラッパ @0xA012BE14 の実読**: submit 失敗時に `lw $a0,-0x6BB4($gp); jal free`
   で request を解放する＝ハンドラの拒否時 free 経路は純正イディオムの複写で正しい。
6. **書込みイディオム（$gp 非依存の絶対導出）**:
   - state: @0xA012B090 `lui 0x8023 / addiu 0x7ED8` → 0x80237ED8 を mask/base
     イディオムで KSEG1 化し、`sw $s0,-0x6B70($gp)` で格納。直後に
     memset($s0, 0, **0x190**) ＝ N-044 の状態構造体サイズと一致。
   - pool: @0xA01524E4 `lui 0x8023 / addiu −0xDAC` → 0x8022F254 を同様に
     KSEG1 化し、`sw $v0,-0x6BB4($gp)` で格納。
   → 2グローバルの「格納される値」まで実バイトで確定（次回の事前確認の予測値になる）。
7. **コールバック呼出し部位 @0xA0124840–4868**: `lw $v0,-0x6B70($gp)` で state を
   引き、`+0x130 → +0x134` の確定コピーをしてから job 走査に入る。
   ハンドラのコールバック前提（+0x134 確定後に呼ばれる、state は同グローバル経由）は正しい。

## file ビルドとの対照（参考、訂正不要の確認）

file イメージ側は $gp = **0x8022DC60**（stream とは 0xA0 差）、状態構造体は
**0x80237FE8**（stream は 0x80237ED8、0x110 差）で、N-044 の file 側記述は
file ビルドとしては正しかった。2つのビルドはデータ配置が実際に違う。
（なお modeq_handler.asm 冒頭の旧記述「$gp(file) 0x8023DC60」も同じ OR 誤読で、
真値は 0x8022DC60。）

## ハンドラの直し（modeq_handler.asm に適用済み）

- 4箇所の `lui 0x8023` → `lui 0x8022`（gate の state 読込み、alloc の pool 読込み、
  拒否時 free の pool 読込み、コールバックの state 読込み）。オフセット
  0x7050 / 0x700C は不変で、指すアドレスが 0x80227050 / 0x8022700C になる。
- **防御の追加（設計判断）**: gate とコールバックの state デリファレンス直前に
  ポインタ健全性チェック（`srl/addiu/sltiu` で KSEG0/KSEG1 帯＝>>29 が 4 か 5
  かを検査、不合格ならデリファレンスせず error 4 / error 3 でクリーンに失敗）を
  追加した。今回の障害は「誤ったポインタのデリファレンスでワーカーが死ぬ」形
  だったため、未知の誤りが残っていても例外ではなくエラー応答に倒すための措置。
  ハンドラ +5 命令、コールバック +5 命令。不要と判断されれば該当ブロックを
  削るだけで戻せる（コメントで明示してある）。
- 冒頭シンボル表も真値に更新し、誤読の経緯をコメントに残した。
- 材料の再構築（build_modeq.py の再実行）は親側で行う。本メモと asm 差分が対象。

## 再挑戦時の事前確認手順（実機投入前、健全な純正ブートで実施）

spot 読み（spot1.py 相当の APER 読み）で、Stage B 完了後（セッション確立後）に:

1. `read32(0x80227050)` → **0xA0237ED8** と完全一致すれば PASS。
   phys 部（& 0x1FFFFFFF）が 0x237ED8 でない場合は即中止（材料を疑う前に座標系を疑う）。
2. `read32(state+0x118)` の bit1 (0x2) が立っていること（ATR 解析済み＝submit の
   ゲートと同一条件）。`read32(state+0x110)`／`+0x114`（NS/NR）が小値（< 0x100）、
   `+0x130`／`+0x134` が 0x200 以下で筋が通ること。
3. `read32(0x8022700C)` → **0xA022F254** と完全一致すれば PASS。
   追随読み `read32(pool)` と `read32(pool+0x14)` が、それぞれ 0 か
   phys < 0x3F00000 の VA であること（記述子としての健全性）。
4. **陰性対照**: `read32(0x80237050)` == 0x2B75AAC9、`read32(0x8023700C)` ==
   0x2B55A2C9 を確認する（前回実験と同じ座標系で読めていることの担保。
   これが違えば座標系が変わっているので中止）。
5. ctx アンカ再確認: `read32(0x80253308)` = head がアンカ自身でなく、
   `read32(head+0x30) & 0x10 != 0`。
6. 1–5 が全て PASS のときだけパッチイメージをブートする。ブート＋セッション
   確立後、**Func 0x04 を発行する前に** 1–3 を再実施し、値が不変であることを
   確認してから発行に進む。1つでも FAIL なら発行せず純正へ復帰して報告する。
