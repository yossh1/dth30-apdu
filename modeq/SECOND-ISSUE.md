# SECOND-ISSUE — Func 0x04 #2 wedge の机上切り分け（2026-11-23、静的解析のみ）

対象: artifacts/modeq-exp2-20261123/SUMMARY.md の未同定事項
（#1 完全成功の直後に書かれた fault 記録 0x8018276c／0x802a9038 の発生箇所）。
材料は stream ビルド（modeq-impl/work/stream_base.bin、VA = 0xA0100000 + offset）の
実バイト逆アセンブルで全て裏取りした。実機には触れていない。

## 0. 結論（先に）

- fault 記録は CPU 例外の記録ではなく、ファーム各所に埋め込まれた
  **fatal 記録ブロック（assert マクロ）** の書込み。exp2 の発生箇所は
  **ジョブ unlink 関数 0xA0182620 の prev リンク整合性チェック（サイト 0xA018276C）**
  とピンポイントで同定できた。純正コード側のチェックで、ケーブ／ハンドラ内ではない。
- 発火タイミングは **#2 の発行時ではなく、#1 の完了後処理（SM の teardown で
  自ジョブを unlink する段）**。hw36_BB.log の時系列（応答回収直後の trace 読みで
  既に新記録）と静的な完了パスの形が一致する。
- 最有力の前提違反は **ctx のエイリアス不一致**: ハンドラはアンカリスト走査で得た
  KSEG0 形の ctx（0x802BD010）をそのまま submit に渡したため、job+0x1C に
  KSEG0 形のヘッドポインタが書かれた。unlink のチェックはヘッドを
  **KSEG1 正規形（phys マスク＋0xA0000000）** で再計算して比較するため不一致になる。
  ただし発火にはゲート `*(ctx+0x14) >= 0` が開いていたことが必要で、これは
  ランタイム値のため机上では確定できない（§5 に切り分け観測を提示）。
- NS/NR の 1/1→0/0 と RX 欄の 0x41 残留は、完了パスの通常分岐で説明がつく
  （§4）。異常の本丸は unlink assert の1点。

## 1. fault 記録の正体

トレースページ（phys 0x530、8 dword）の形式は、記録ブロック自身のコードから確定:

| idx | phys | 内容 |
|---|---|---|
| 0 | 0x530 | 0xDEADC0DE（マジック） |
| 1 | 0x534 | **ブロック自身の KSEG0 アドレス**（lui/addiu で自己アドレスを定数構築） |
| 2 | 0x538 | 記録時点の **$sp** |
| 3 | 0x53C | 補助関数 0xA01E7BB4 の戻り値（両回とも 0） |

- 書込みは phys 0x530（共有ページ、KSEG1 側 0xA0000530）と phys 0x100530
  （イメージ側、0xA0100530）の両エイリアスへ二重に行われる。
- ブロックのイディオム（lui $s1,0xdead / ori 0xc0de …）はイメージ全域に
  **138 箇所**（0x3C11DEAD の出現数、Func 0x04 スタブ本体を含む）あり、
  各チェック箇所に埋め込まれた fatal マクロ。
- ブロック実行後、呼出しタスクは通常処理へ戻らない。unlink のサイトでは
  記録後に共有メールボックス（phys 0xA10、FEEDFEED マジック）監視＋
  スリープ（0xA01E6400、引数 0x64/0x66）の駐車ループへ落ちる。
  ＝そのタスクは実質死亡し、wedge になる。
- exp2 の $sp = 0x802a9038 は exp1 の 0x802a90a8 と近傍（差 0x70）で、
  同一タスクスタック域の異なるコール深度とみて矛盾しない（傍証レベル）。

### exp1 の記録（0x801deb38）との比較

- exp1 のブロックは 0xA01DEB38 で、直前は「0x90 バイトの構造体を phys 0x560
  （トレースページの直後）へコピー → 0xA01E6F00 呼出し → 無条件に記録ブロック」
  という並び。チェック分岐に挟まれたインライン assert ではなく、
  **診断スナップショット付きの致命的エラー報告ルーチンの末尾**にある。
- つまり exp1 は「ワーカの不正デリファレンス（例外）を起点に報告ルーチン経由で
  記録された」構図と整合し、記録アドレスは障害箇所そのものではない。
  （報告ルーチンの呼出し元の同定まではできていない＝未確定。）
- exp2 は逆に、チェックの失敗箇所そのものが記録されるインライン型で、
  発生箇所を1命令単位で同定できる。両者は「同じ記録形式、別の機構」。

## 2. exp2 サイトの同定: unlink 関数 0xA0182620

### 2.1 前提となる構造（submit 0xA0121700 と insert 0xA0181EE4 の実読で確定）

ジョブ投入で作られるジョブディスクリプタ（プール確保）の主要フィールド:

| offset | 意味 | 書込み手 |
|---|---|---|
| +0x08 | セッションオブジェクト VA（KSEG0、符号付きで負） | insert @0xA0181F3C |
| +0x0C | 状態: 0x100=保留 / 0x101=待ち / 0x102=アクティブ（スロット保持） | submit / insert |
| +0x10 | フラグ（bit0 が立つと unlink はリンク操作をスキップ） | submit で 0 |
| +0x14 | セッションのスロット番号（投入時は −1、insert で割当て） | insert |
| +0x18 | **ctx**（submit の第1引数、そのまま格納） | submit |
| +0x1C | prev リンク（ctx リスト） | insert |
| +0x20 | next リンク（ctx リスト） | insert |
| +0x24 | request オブジェクトへのポインタ | submit |
| +0x2C | 完了コールバック（aux） | submit |

リストは2系統ある:

- **ctx リスト**: ヘッドは **ctx+0x0C に埋め込み**（ヘッドのリンク欄は
  ctx+0x28=prev / ctx+0x2C=next として効く）。ジョブのリンクは +0x1C/+0x20。
  insert は先頭に挿入する（0xA0181F1C–1F38）:
  `job->prev = ctx+0xC; job->next = head->next; (head->next)->prev = job; head->next = job`。
  ここで `ctx+0xC` は **job+0x18 に格納された ctx 値をそのまま** 使う
  （＝submit へ渡されたエイリアス形がそのままリンクに残る）。
- **セッション待ちリスト＋スロット**: セッション +0x00/+0x04 が双方向リストの
  アンカ対、+0x0C がスロット bitmap、+0x14 がリングマスク、+0x18 が次スロット
  番号、**+0x1C+idx*4 がスロット表**（アクティブジョブはここから引かれる。
  SM が session+0x1C を現行ジョブとして読む @0xA012486C の観測と一致）。
  スロットが空いていれば待ち先頭（無ければ新規ジョブ）がアクティブに昇格し、
  insert の戻り値として submit 側が 0xA0121264（ジョブ開始）へ渡す。

### 2.2 unlink 0xA0182620（session, job）のチェック列

呼出し元は12箇所: purge 0xA0124210 内（0xA0124258/4290）、SM 内7箇所
（0xA01243DC/45E8/4654/4A80/4B5C/4BC8/4E54。全て現行ジョブ $s1 を対象とする
teardown 系）、他モジュール3箇所（0xA0145D6C/0xA0152F18/0xA0153D84）。

入口ガード（どちらも「リンクを触らずスロット解放だけして帰る」経路 0xA0182968 へ）:
- job+0x18（ctx）== 0、または job+0x10 bit0 が立っている。

整合性チェック（対象は job の前後リンク）:
- チェックA（サイト 0xA0182664）: job+0x08 が負でない
  （＝セッション VA が入っていない）→ assert。
- チェックB（サイト **0xA018276C** ＝ exp2）: prev = job+0x1C について、
  `*(prev+8) >= 0` のとき（prev が通常ジョブでない＝ヘッド側とみなすとき）だけ、
  `prev == (0xA0000000 + (ctx & 0x1FFFFFFF)) + 0xC` でなければ assert。
  通常ジョブの +0x08 はセッション VA（負）なので、prev がジョブなら素通りする。
- チェックC（サイト 0xA0182878）: next = job+0x20 について同型。

チェック通過後: prev/next の付け替え（+0x1C/+0x20）、スロット表エントリの
クリア、bitmap ビットのクリア、昇格処理 0xA01824C4 呼出し、復帰。

**exp2 の assert はチェックB**: teardown 対象ジョブの prev が「ヘッドのはず」
なのに、KSEG1 正規形で再計算したヘッドアドレスと一致しなかった。

## 3. 発火タイミングの同定

hw36_BB.log の時系列:
- 23:32:10 Func 0x04 #1: 受理 0.010 秒、応答完了 0.072 秒、応答回収。
- その直後の trace 読み（#1 ブロックの "trace after"）で **既に新記録**
  （0x8018276c／0x802a9038）。
- 続く #2（同 23:32:10 発行）はドアベルがラッチされたまま受理されず、
  10 秒タイムアウト。PEND・status は未書込み。

＝ assert は #2 の処理中ではなく、**#1 の応答が揃った後の完了後処理**で発火し、
カードタスク側が駐車したため #2 が処理されなかった、という読みが唯一整合する。
（#2 の slot 着地は PASS しており、ホスト側の発行手順の問題ではない。）

## 4. #1 完了後の後処理（静的に辿った流れ）

SM の受信完了パス（0xA0124840〜）:

1. `state+0x130 → state+0x134` に確定コピー（@0xA0124864–68）。
2. 現行ジョブを session+0x1C から取得（@0xA012486C）、request = job+0x24。
3. job+0x2C のコールバックを `jalr`（$a0=0, $a1=request、@0xA01248AC）。
   ← ハンドラのコールバックはここで応答を slot へ書いた（#1 成功の段）。
4. 完了分岐: job+0x10 bit0、request+0x80（センチネル −1 か）等で分岐。
   センチネルが残っていれば write-back 0xA0123F08（ctx=request+0x8C、a1=1、
   @0xA01248F4–FC）。処理済みなら T=1 シーケンス処理へ:
   - NR の更新（state+0x114、@0xA0124914–）や、S ブロック応答時の
     NS 設定（@0xA0124A24: `state+0x110 = (block>>4)&1`）。
   - **NS/NR ゼロクリア分岐（@0xA0124A58/5C）**: request+0x88 の種別と
     状態バイトの条件が合うと `state+0x110 = state+0x114 = 0`。
     wedge 観測（NS/NR 1/1→0/0、RX +0x130/+0x134 に #1 の総量 0x41 が残留）は
     この通常分岐＋「RX 欄は次回受信まで残る」仕様で説明でき、異常ではない。
5. **teardown（@0xA0124A60〜）**: ロック取得 → **unlink(session, job)
   @0xA0124A80** → ロック解放（戻り値は次ジョブ）→ free(pool, job)
   @0xA0124AA4 → free(pool, request) @0xA0124AB0 → 次ジョブがあれば
   0xA0121264 で開始（@0xA0124AC0）。
   別経路の teardown も同型（0xA01245E8/4B5C/4E54 等、エラー／中断系）。
   **ジョブディスクリプタと request の解放はコールバックの後、unlink の後**で、
   解放自体は通常処理。キューの残留物は無い（unlink がスロット表と bitmap
   まで戻す）。

→ #1 の後処理で「前提を満たさずに進む」余地があるのは、実質 teardown の
unlink チェックだけ。他の段（コールバック、write-back、NS/NR、解放）は
観測どおり正常に進んだ形跡がある（応答回収済み、NS/NR は通常分岐の結果）。

## 5. 「#2 の投入が踏んだ前提違反」の候補

正確には「#1 の teardown が踏んだ前提違反」。優先順位つき:

### 候補1（最有力）: ctx のエイリアス不一致（KSEG0 で渡した）

- ハンドラはアンカ 0x80253308 のリストを KSEG0 のまま走査し、先頭ノード
  0x802BD010（実機 spot で確認）を ctx として submit に渡した。
- insert は job+0x1C = ctx+0xC を **渡された形のまま**（= 0x802BD01C）書く。
- teardown の unlink チェックBは、期待値を
  `0xA0000000 + (ctx & 0x1FFFFFFF) + 0xC` = **0xA02BD01C** と再計算する。
  prev（0x802BD01C）と一致しない → assert。
- 傍証: ファームの「格納・比較されるポインタ」の正規形は KSEG1
  （state-ptr 格納値 0xA0237ED8、pool-ptr 格納値 0xA022F254 はどちらも KSEG1。
  ラッパ隣接コード @0xA012BE44 も ctx を mask+base で KSEG1 化して使う）。
  一方アンカリスト（チャネル一覧）は参照専用で KSEG0 リンクのまま使われる
  （reset 関数 0xA0125938 はノードを KSEG0 のまま読むだけ）。
  「参照は KSEG0、投入は KSEG1」という使い分けにハンドラが乗り損ねた形。
- **未確定要素**: 発火にはゲート `*(ctx+0x14) >= 0` が必要。ctx+0x14 は
  ランタイム値で机上では読めない。また純正 submit 呼出し元の ctx の出所は
  スタック保存引数までは追えたが、生成側（チャネルオブジェクト生成時に
  どちらのエイリアスで保持されるか）の確定には至っていない。
  - もしゲートが通常閉じているなら、純正ジョブが KSEG0 で渡していても
    assert は起きず、本候補は崩れる。その場合に残るのは候補2。
  - 机上でさらに裏取りできること: チャネルオブジェクトの生成／初期化
    （ctx+0x28/+0x2C へのヘッド自己リンクの書込み箇所）の同定が残っている。
    初期化が KSEG1 で自己リンクを書いていれば正規形の傍証が強まる。
    本便では未完（次の一手に残す）。
  - 実機で一撃の観測（次回、読み取りのみ）: Stage B 中の純正ジョブについて
    job+0x18（ctx）と job+0x1C（prev）の実値、および *(ctx+0x14) を spot 読み
    すれば、エイリアス形とゲートの両方が確定する。

### 候補2: prev がヘッドでもジョブでもない値だった（リスト破壊型）

- 例: 自ジョブが ctx リスト先頭にいる間に別の挿入／削除が割り、
  prev が解放済みブロックや別構造を指した、等。
- ただし観測上、#1 の窓（0.072 秒＋回収直後）で完了したジョブは自ジョブのみで、
  発行系は hw36 しか動いていない。静的にも、insert/unlink は同一ロック
  （0xA01E5A34）で保護されており、通常経路の競合では壊れない作り。
  候補1のゲートが閉じていた場合の受け皿として残すが、積極的な根拠は無い。

### 候補3: 二重 teardown／別経路からの再 unlink

- SM には teardown 型の unlink 呼出しが複数ある（完了系 0xA0124A80、
  エラー系 0xA01245E8/4E54、purge 等）が、いずれも「現行ジョブ（session+0x1C）」
  を対象に1回だけ通る構造で、二重に通る静的証拠は見つからなかった。
  また2回目の unlink は入口ガード（job+0x10 bit0 は teardown で立たない／
  ctx は残る）では防げないものの、発生条件の根拠が薄い。優先度は低い。

### 候補4: NS/NR ゼロクリア分岐との競合

- NS/NR クリア自体は通常分岐（§4-4）で、unlink の前提（リンク値）とは
  無関係。因果は薄い。観測の説明としては採用、原因候補としては棄却寄り。

## 6. 再挑戦の設計案（優先順位つき）

### 案1（本命）: ハンドラの ctx を KSEG1 正規形に変換してから使う

- 変更点は1箇所: mq_find で対象ノードを見つけた直後（mq_found）、
  submit と request 充填の両方が使う $s1 を KSEG1 化する。
  走査中の sentinel 比較（アンカ自身との beq）は KSEG0 のまま行うので、
  変換は発見後に置くこと。
- asm 差分の形（+2 命令、PEND／CB のオフセットは不変）:

```
mq_found:
    ; NEW (SECOND-ISSUE candidate 1): canonicalize ctx to its KSEG1 form.
    ; The job-list machinery stores job+0x1C = ctx+0xC verbatim, and the
    ; unlink consistency check recomputes the head as
    ; 0xA0000000 + (ctx & 0x1FFFFFFF) + 0xC. A KSEG0 ctx (as found by
    ; walking the 0x80253308 anchor list) therefore fails the check at
    ; teardown and parks the card task. The anchor list itself is
    ; KSEG0-linked, so $s1 is known to be 0x80xxxxxx here and a plain
    ; OR with 0xA0000000 is the exact conversion.
    lui   $t7, 0xA000
    or    $s1, $s1, $t7
    ; req = alloc(...)   (以下従来どおり)
```

- 効く範囲: job+0x18（ctx）、insert が書く job+0x1C（prev=ヘッド）、
  request+0x8C（write-back 用 ctx。参照のみだが正規形に揃う）が全て
  KSEG1 形になる。コールバック／ゲート／PEND には影響しない。
- 前提: 候補1が正しいこと。ゲートが閉じていた場合は無害な変更に留まる
  （デリファレンスはどちらのエイリアスでも同じ物理を指す）。

### 案2（案1と抱き合わせの事前観測）: 純正ジョブのリンク実読

- 次回実機の最初に、読み取りのみで: Stage B 実行中に純正ジョブ
  （ECM 等）のディスクリプタを session+0x1C から辿り、
  job+0x18／job+0x1C の実値（エイリアス形）と *(ctx+0x14)（ゲート）を
  spot 読みする。候補1の未確定要素2点が実測で確定する。
- 案1の変換要否はこの観測で決められる。観測が KSEG0 を示した場合は
  候補1が崩れるので、案1を入れず候補2の観測設計に切り替えること。

### 案3（棄却）: 発行間隔を空ける／ホスト側の待ち条件

- assert は #1 の teardown（完了直後）で発火しており、#2 との間隔は
  無関係。間隔・待ちでは防げない。採用しない。

### 案4（机上の残件）: チャネルオブジェクト初期化の同定

- ctx+0x28/+0x2C（ヘッド自己リンク）の初期化書込み箇所を静的に同定し、
  正規エイリアスの傍証を固める。実機観測（案2）の方が速いため優先度は低い。
