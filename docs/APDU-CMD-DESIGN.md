対象コード: `mikosu/driver/`（master ef207fcd、DTH10-series-driver）の

## 0. 判定の要旨

- **設計は成立する。** 彼の FW にはカードの T=1 状態機械（card.rs）が完成して
  おり、不足しているのは「任意 APDU の投入口」「完了通知の経路」「ATR の
  読み出し口」の3点だけで、いずれも既存の配管（コマンド 11 の非同期型、
  M2H メッセージ、open の payload 書き戻し）の型に乗せて追加できる。
- **v1 の範囲**: 送信 APDU ≤ 60 バイト、応答は送受信合計 ≤ 127 バイトに
  収まるもの、T=1 連結（送信・応答とも）なし、同時実行 1 つ。
  INITIAL_SETTING（5 バイト → 応答 61 バイト）はこの範囲の内側にある。
- **上限の律速は RAM でもイメージサイズでもなく、カード経路の2つの
  ハード寄り制約**（送信 FIFO 64 バイト、MMR 0x1034 の mod 128 カウンタ）。
- **競合の結論**: 外部 APDU は ECM と同じジョブキューに投入して直列化する
  （セッション共有）。「アイドル時のみ許可」は採らない（§4）。
- 未確定点は §8 に集約した。推測で埋めた箇所はない。

## 1. 現行プロトコルの把握

### 1.1 転送経路（チップ ↔ ホスト）

純正と同じ MMR ドアベル方式（`dth30-fw/src/host.rs`、`dth30-core/src/vixs/cmd.rs`）。

- ホストはコマンドリングのスロット（SLOT_SIZE 0x23C0、payload は +0x24 から、
  最大 0x239C バイト）にコマンドを組み、MMR 0x3030 にスロット物理アドレス、
  0x3020 に func 番号を書く。FW はスロット +0x0C のコマンド ID と +0x14 の
  payload 物理アドレスを読む。
- 完了はスロット +0x10 への結果書き込み（OK=1 / FAILED=2 / UNSUPPORTED=5）と
  MMR 0x3048 / 0x302C で通知される。**ホスト・FW とも同時実行は1コマンドのみ**
  （ホスト側は `pending` チェック、FW 側はメインループの逐次処理）。
- コマンドハンドラはメインループ内で同期的に呼ばれる。したがって
  **ハンドラは長時間ブロックできない**（§3.2 の非同期化の根拠）。
- 逆方向は M2H メッセージ: 本体 8 個 × 0x280 バイト（SDRAM 0x61000〜）、
  記述子は本体 +0x24 から 0x25C バイト。同時に outstanding は1つだけで、
  ホストの ACK で次が送られる。

### 1.2 コマンド番号の現状

FW のディスパッチ（`dth30-fw/src/main.rs` の `Firmware::command`）:

| ID | 意味 | 状態 |
|---|---|---|
| 0 | ping | 実装済み |
| 1, 2, 3, 5 | — | UNSUPPORTED を返す（純正にあって未実装の予約枠） |
| 8 | ストリーム open（Raw / Program） | 実装済み |
| 9 | ストリーム close | 実装済み |
| 10 | flush | 実装済み |
| 11 | CAS オブジェクトへの入力 | 実装済み（カードリセットのみ、§1.4） |
| 24 | TS 入力設定 | 実装済み |
| 25 | CAS オブジェクト open | 実装済み |
| 26 | CAS オブジェクト close | 実装済み |
| 27 | OTP 署名 | 実装済み（スロット無し、ドアベル直通） |
| その他 | — | FAILED |

ホスト側の func 定数（cmd.rs）には他に 13 (OUTPUT_REQUEST)、20
(INTERNAL_CONTROL)、21 (TS_CONTROL)、22 (I2C_DEVICE) が純正の番号として
定義されているが、彼の FW は実装していない（FAILED が返る）。
**どの資料にも現れない番号: 4, 6, 7, 12, 14–19, 23, 28 以上。**

### 1.3 M2H メッセージ ID の現状

| ID | 意味 | ホスト側の扱い |
|---|---|---|
| 0x00 | READY（起動完了） | 起動処理 |
| 0x05 | ALLOC_FB（起動時） | 起動処理 |
| 0x0C | DATA_READY | cmd.rs の `stream_message` が内部処理 |
| 0x0E | STREAM_STATUS | 同上 |
| 0x0F | INPUT_DONE（コマンド 11 の完了） | 同上 |
| その他 | — | `set_m2h_handler` で登録したハンドラへ |

- ホスト側の制約: メッセージ ID は M2H_ID_LIMIT (0x1C) 未満。
- **`set_m2h_handler` の登録者は本番コードにはいない**（grep で確認）。
  使われているのは `cmd.rs` の単体テスト2件のみ（0x17 のカスタム ID が
  ハンドラへ届くことの検証）で、そのテストが受け口の動作実証になっている。
  つまりカスタム ID の受け口は空いている。
- 注意: 0x0F は `stream_message` が「ハンドルの書き換えと ACK」だけを行い、
  **記述子の結果ワード（後述の result）は現在の利用者に渡らない**。
  APDU の完了通知を 0x0F に相乗りさせる案は、ホスト側の内部処理の改修が
  必須になるため採らない（§3.2）。

### 1.4 雛形: コマンド 11（カードリセット）の配管

ホスト側 `build_card_reset`（`dth30-core/src/vixs/stream.rs`、INPUT_LEN 0x2DC）:

| payload | 値 | 意味 |
|---|---|---|
| +0x00 | CAS ハンドル（FW 払い出し値 0xA0062A40） | 照合用 |
| +0xA0 | 0x10000 (INPUT_KIND_CAS) | 入力の種別 |
| +0xB0 | 512 | （FW は読まない） |
| +0xB8 | 16 (REQUEST_CARD) | 要求フラグ |
| +0x1BC | 1 | bit0 = カードリセット要求 |
| +0x1C0 | 1 | （FW は読まない） |

FW 側 `Cas::input`（`dth30-fw/src/cas.rs`）:

- +0xA4 を 0 クリアし、ハンドル / kind / flags を照合。合致しなければ
  **黙って OK を返す**（未対応ビットも同様）。要求ワード（+0xA0, +0xAC,
  +0xB8）を `Object.request` に控え、+0x1BC bit0 があれば
  `card.request_reset()` を呼ぶ。コマンド自体は即 OK。
- 結果は非同期: Card が `Output::ResetDone(result)` を出すと
  `Cas::card_output` がメッセージ 0x0F を組み、記述子に cookie（+0x00/+0x04、
  open 時にホストが渡した2ワード）、要求エコー（+0x08/+0x1C/+0x24）、
  結果（+0x20）を書いて送る。

この「即 OK + メッセージで完了通知」が、本設計の APDU 交換の雛形になる。
ただし2点だけ流儀を変える: ①完了通知は新規 ID を使う（§1.3 の理由）、
②受理できない場合は黙って OK にせず理由を返す（能力検出のため。ホストが
旧 FW と改造 FW を区別できることが、橋渡しソフトの前提になる）。

## 2. カード駆動の現状（dth30-fw/src/card.rs, cas.rs, program.rs）

- **所有と駆動**: `Firmware` 構造体が `Card` を所有し、メインループが毎周
  `card.poll()` を駆動する。Card の出力（`Output`）は毎周 `take_output` で
  取り出され、`Cas::card_output` と `Program::card_output` の両方へ配られる
  （Cas は ResetDone / InitDone を、Program は Keys / EcmRefused / EcmLost を
  消費し、相手の分は無視する）。
- **セッション管理**: Card は Phase 状態機械（Idle / PowerOff / PowerOn /
  Atr / PpsGap / Pps / Gap / Wait）と、深さ4のジョブキュー
  `[Job; 4]`（Resync / Ifs / Init / Ecm の固定 enum）を持つ。
  活性化（ATR 確定）時に Resync → Ifs → Init が投入され、Init の応答から
  システム鍵と CBC 初期値を鍵 RAM へ書く。INIT 完了は CAS イベント
  （EV_INIT + リターンコード）としてホストへ報告される。
- **APDU の発行主体は FW 内のみ**: INITIAL_SETTING は `Job::Init` として
  ハードコード（`90 30 00 00 00`）、ECM は `Program` が TS から取り出した
  body を `Card::submit_ecm` で投入し、card.rs が `90 34 00 00 Lc body Le`
  に組み立てる。ホストは APDU バイト列を一切見ない。
- **ECM の規約**（§4 の根拠）: Program は前回と異なる body のときだけ投入
  する。送信中の ECM は差し替え不可、待ち行列中の ECM は新しい body に
  差し替わる。失敗時は `EcmLost` が返り、Program は「前回 body」の記録を
  消すので、次の ECM 繰り返しで同じ body が再投入される。鍵 RAM は
  `Keys` が来たときだけ更新され、`EcmLost` では旧鍵が残る。
- **ATR は保持されない**: Phase::Atr で受信バッファ `rx` に集め、
  `parse_atr` が ta1 / ta2 / ta3 / protocol だけを抽出して使い、生バイトは
  破棄される（`rx` は次のブロック受信で上書きされる）。読み出し口は
  存在しない → §5 で新設する。
- **応答の連結は未対応**: 受信側は I ブロックの M ビット（0x20）が立って
  いれば「ok でない」として扱う（card.rs の `response`）。送信側の連結も
  ない（1 回の `send` で1ブロックのみ）。IFS 要求で 0xFE を出しているため
  B-CAS の応答は1ブロックに収まる前提の設計。
- **カードの状態**: `Card::status()` が PRESENT=1 / ACTIVE=2 を返す。
  CAS イベント（EP 0x82 のブロック、ヘッダ +0x88 のフラグ INSERTED
  0x2000 / REMOVED 0x4000 / ACTIVATED 0x8000 / INIT done 0x800000）は
  ホストに見えるが、これは状態通知であって APDU の口ではない（DESK.md §3.4）。

## 3. APDU コマンドの設計

### 3.1 番号の選定

- **コマンド ID = 28**。理由: 0–27 は純正 RPCI の Func 番号体系と対応づいて
  おり（彼の func 定数表がそのままそれ）、28 はその 0–27 の番号体系の
  外側にある最初の番号。1/2/3/5 は「純正にあって未実装」の予約枠（UNSUPPORTED を返す
  実装済みの意思表示）なので流用しない。4 は純正で DEADC0DE スタブだった
  番号であり、我々の Mode Q が純正側で使った番号でもあるため、混同回避の
  ため使わない。
- **完了メッセージ ID = 0x10**（新規、名称案 APDU_DONE）。0x1C 未満の制約の
  内側で、現行の使用済み ID（0x00/0x05/0x0C/0x0E/0x0F）と重ならない。
  純正 FW での 0x10 の意味は未確定（§8 U1）だが、本コマンドは彼の FW 上で
  のみ動くため、彼の ID 空間での空きをもって選定する。

### 3.2 方式: 非同期（submit + 完了メッセージ）

コマンド 28 は「投入」と「照会」の2つの op を持ち、交換自体は非同期に
完了する。同期ブロッキングにしない理由:

- T=1 のブロック応答は最大 ~1.4 秒かかり、WTX 延長でさらに伸びる
  （card.rs の Wait 期限は 1500 ms）。メインループは DMA・TS リング・
  5 ms ハートビートも回しており、ハンドラ内で待つとストリームと
  ホスト側の hang 検知（HANG_TICKS）に影響する。
- コマンド 11 が同じ理由で非同期型になっていると読める（即 OK + 0x0F）。

### 3.3 コマンド 28 の payload 形式

スロット payload 先頭からのオフセット。+0x00 のハンドル照合はコマンド 11
と同じ流儀。FW は入力を読んだ後に同じ payload へ書き戻す（open が
ハンドルを書き戻す先例がある）。

| offset | 方向 | 内容 |
|---|---|---|
| +0x00 | 入力 | CAS ハンドル（コマンド 11 と同じ照合） |
| +0x04 | 入力 | op: 0 = EXCHANGE、1 = QUERY |
| +0x08 | 入力 (EXCHANGE) | APDU 長（1..=60、§3.5） |
| +0x0C | 入力 (EXCHANGE) | tag: ホストが選ぶ u32。完了メッセージにエコーされ、陳腐化した完了の破棄に使う |
| +0x10.. | 入力 (EXCHANGE) | APDU バイト列（CLA INS P1 P2 [Lc data] [Le] の生 APDU） |
| +0x08 | 出力（書き戻し） | 理由コード（§3.6 表1）。0 = 受理 / 正常 |
| +0x0C | 出力 (QUERY) | カード状態フラグ（bit0 = PRESENT、bit1 = ACTIVE。`Card::status()` と同じ値） |
| +0x10 | 出力 (QUERY) | ATR 長（0 = 未取得） |
| +0x14.. | 出力 (QUERY) | ATR バイト列 |

- コマンド自体の結果（スロット +0x10）は OK / FAILED / UNSUPPORTED で、
  FAILED のとき payload +0x08 に理由コードが入る。op が未知なら
  UNSUPPORTED を返す（旧 FW はコマンド 28 自体に FAILED を返すので、
  ホストは「コマンドの有無」を区別できる）。

### 3.4 完了メッセージ APDU_DONE (0x10) の記述子

コマンド 11 の ResetDone と同型（cookie で CAS オブジェクトに紐づける）。

| offset | 内容 |
|---|---|
| +0x00 / +0x04 | cookie（CAS open 時にホストが渡した2ワード） |
| +0x08 | tag エコー（submit 時の +0x0C） |
| +0x0C | 完了コード（§3.6 表2） |
| +0x10 | 応答長（完了コード 0 のときのみ有効） |
| +0x14.. | 応答 APDU（データ + SW1 SW2。**SW は FW が解釈せず素通し**） |

記述子領域は 0x25C バイトあるため、応答上限（§3.5）でも十分に収まる。

実装上の注意（ResetDone の流儀を流用しない点）: ResetDone はメッセージ
本体の確保に失敗すると黙って捨てるが、APDU の完了を捨てるとホストが
無限待ちになる。**APDU_DONE は確保に失敗したら保持して次の周回で
再試行すること**（Card の `out` キューに残す形が自然）。

応答実体の受け渡し: Card の `rx` は次のジョブの受信で上書きされるため、
`response()` の時点で応答 INF を専用バッファ（`apdu_rx`）へコピーし、
APDU_DONE の組み立て時に Cas がそれを参照する形にする（§7 の作業分解）。

### 3.5 扱える APDU 長の上限

律速は2つともカード経路の制約で、RAM ではない。

1. **送信: APDU ≤ 60 バイト**（T=1 の1ブロック INF ≤ 60）。
   根拠: 送信 FIFO は 64 バイトで、ブロックは NAD + PCB + LEN + INF + LRC
   = INF + 4 バイトを一括で書いてから送信コマンド（MMR 0x1030）を出す
   構造（card.rs の `send`）。彼の ECM_MAX = 54 が APDU 換算でちょうど
   60（ヘッダ5 + body 54 + Le 1）なのはこの制約と一致する。
2. **受信: 送信ブロック長 + 応答ブロック長 ≤ 127 バイト**（現行実装の
   安全域）。根拠: 受信の進捗は MMR 0x1034 の bits 6..0（送受信合計の
   mod 128 カウンタ）で数える実装（card.rs の `pull`、および電源断時の
   「計数が 128 に戻るまで送信部が動き続ける」という同ファイルの
   コメント）。`rx` バッファ自体は 260 バイトあり、IFS 要求 0xFE の
   建前では応答 INF ≤ 254 バイトだが、カウンタの wrap を扱う実装が
   ないため、合計 127 バイトを超える交換は現行の `pull` では正しく
   数えられない。
   - INITIAL_SETTING は送信ブロック 9 + 受信ブロック 65 = 74 バイトで
     内側（Mode Q の実証値とも整合）。
   - 応答ブロックの LEN が判明した時点で合計超過が見えたら、その交換は
     完了コード 2（交換失敗）とする。黙って切り捨てない。
3. 送信連結・応答連結は v1 では扱わない（応答に M ビットが立てば
   完了コード 4）。127 バイト超の応答と連結の解禁は、`pull` の wrap
   対応と card.rs への連結実装が前提の v2 項目。

RAM とイメージの見積もり: 追加バッファは APDU 保持 60 + 応答コピー
最大 124 + ATR 34 で 220 バイト級、コード追加は 1–2 KB 級の見積もり。
FW イメージは現行 25,312 バイトで、SDRAM 配置はイメージ 0x100000〜に
対しリングが 0x800000〜（`dth30-fw/README.md` のメモリ表）であり、
**容量は律速にならない**（見積もりであり実測は実装フェーズ、§8 U5）。

### 3.6 エラー対応

Mode Q の流儀（状態は小さな整数コード、SW は応答内で素通し、同時実行は
単発）に合わせる。Mode Q との違いは、受理可否が同期的に分かるよう
投入時と完了時の2段に分けた点。

表1: 投入時の理由コード（payload +0x08 書き戻し、コマンド結果 FAILED と対）

| コード | 意味 |
|---|---|
| 0 | 受理（コマンド結果は OK） |
| 1 | カードなし / 未活性（不在、リセット・活性化シーケンス中を含む） |
| 2 | ビジー（交換中、またはジョブキュー満杯） |
| 3 | 長さ不正（0 または 61 バイト以上） |
| 4 | ハンドル不一致 / CAS 未 open |

表2: 完了コード（APDU_DONE +0x0C）

| コード | 意味 |
|---|---|
| 0 | 成功。応答長と応答 APDU が有効 |
| 1 | カード抜去（交換中に不在になった、または完了前に forget された） |
| 2 | 交換失敗（T=1 エラー / タイムアウト。リトライ上限到達。§3.5 の合計超過を含む） |
| 3 | 中断（リセット要求・電源サイクル・guard の再立ち上げに巻き込まれた） |
| 4 | 連結応答（v1 未対応。M ビット付き応答を受けた） |

注: card.rs の `retry` はタイムアウトとブロック破損（LRC 不一致等）を
同じ経路で数えるため、完了コード 2 は両者の統合とする。分離は最後の
失敗原因の記録を追加すれば可能だが、v1 では必須としない。

## 4. 競合の設計判断（最重要）

### 4.1 実態

- カードは単一の T=1 チャネルで、駆動者は Card 状態機械ただ1つ。
  T=1 の状態（ns/nr、通信レート、IFS）は Card の内部変数に集約されている。
- ECM の発行主体は Program（ストリーム open 中のみ）。投入は
  `submit_ecm` 経由で同じジョブキューに入る。キューの深さは4で、
  活性化直後は Resync / Ifs / Init が占める。
- `activate()` は `jobs[..3]` を無条件に上書きし、`power_cycle()` と
  `forget()` は `njobs = 0` でキューを消す。**キューに残ったまま
  これらを踏むと、保留ジョブは無言で消える**（現行の固定ジョブでは
  問題にならないが、外部 APDU ではホストの無限待ちに直結する）。

### 4.2 結論: セッション共有 + ジョブキューでの直列化

外部 APDU は新ジョブ種別 `Job::Apdu` として**ECM と同じキューに投入**
する。別経路（例: 状態機械の外から UART を触る）や、セッションの
複製は作らない。根拠:

1. T=1 状態が1箇所にしかない以上、直列化の単位はジョブキューしかない。
   Mode Q が純正層のジョブ投入に寄せた判断と同じ結論に、彼のコードでも
   なる。
2. ECM への遅延は APDU 1交換分（Wait 期限 1.5 秒 + リトライ + WTX 延長）
   が上限で、ECM 側には自己回復がある: 失敗・遅延しても鍵は旧鍵が残り、
   次の ECM 繰り返し（放送の ECM は周期的に送られる）で再投入される
   （§2）。つまり最悪ケースは「暗号期間の切り替わり付近での一過性の
   乱れ」であり、復号の恒常的な停止にはならない。
3. 「アイドル時のみ許可」（Program open 中は APDU を断る）案は実装が
   楽な代わりに、視聴中の APDU 用途（EMM 受信など）が閉じる。さらに
   「アイドル」の判定に Program の開閉状態を Card の受付条件へ持ち込む
   必要があり、共有案より状態の結合が増える。採らない。

### 4.3 課すガード（実装要件）

1. **受付はカード ACTIVE 時のみ**。リセット・活性化シーケンス中は
   理由コード 1 で即拒否する。これにより §4.1 の `activate()` の
   上書きと保留 APDU が衝突する経路を断つ（活性化前にキューへ
   入ることがない）。
2. **同時実行は1つ**（Mode Q の v1 制限と同じ）。交換中の追加投入は
   理由コード 2。キュー満杯も同じく 2。APDU は `submit_ecm` の
   差し替え対象にしない（差し替えは Job::Ecm 同士のみ、既存ロジック
   不変更）。
3. **順序は FIFO**。APDU が先にキューされた場合のみ ECM が最大1交換分
   待つ。待ち ECM の後ろに APDU が付く場合は ECM の遅延は生じない。
4. **中断の伝播を必須とする**: `power_cycle()` / `forget()` がキューを
   消すとき、保留中の APDU があれば完了コード 3（中断）または 1
   （抜去）を付けた `Output::ApduDone` を必ず発行する。コマンド 11 の
   リセット要求による電源サイクルも同じ扱い（= APDU 交換中のリセット
   要求は APDU を中断させる、と仕様に明記する）。
5. **抜去の検出は既存機構に乗る**: detect（50 ms、2回一致）が forget を
   呼ぶ経路と、Wait の期限（1500 ms）+ リトライが上限を保証する。
   どちらの経路でも §4.3-4 により APDU_DONE が返る。
6. WTX 延長が繰り返されると ECM 遅延の上限は 1.5 秒では閉じない
   （§8 U4）。v1 はこのまま許容し、実測で問題になれば v2 で「APDU
   ジョブの総時間予算（超過したら中断して完了コード 2）」を足す。

## 5. ATR の扱い

- 現状（§2）: 生 ATR は保持されず、読み出し口はない → **新設が要る**。
- 新設の形: Card に `atr: [u8; 34]` と `atr_len: u8` を追加し、
  Phase::Atr で `parse_atr` が Done を返した時点で `rx[..rx_len]` を
  コピーする（Done は完全な ATR が揃ったときにだけ返る）。
  `power_cycle()` / `forget()` で `atr_len = 0` に戻す。
  バッファ 34 バイトは ISO/IEC 7816-3 の ATR 上限（TS + 32 バイト =
  33 バイト）に基づく見積もり（§8 U6）。
- 読み出し: コマンド 28 の op=QUERY（同期、payload 書き戻し、§3.3）。
  新規コマンドをもう1つ作らず op で分けるのは、照会が「状態 + ATR」の
  組で常に一緒に要るため。
- PC/SC 橋渡しでの取得手順（既存フローへの追加は QUERY のみ）:
  CAS open（既存 cmd 25）→ カードリセット要求（既存 cmd 11）→
  ACTIVATED イベント待ち（既存）→ QUERY で ATR 取得 → EXCHANGE で
  APDU 交換。PC/SC の IFD ハンドラは電源投入のたびにこの手順を踏む。

## 6. ホスト側の受け口

### 6.1 dth30-core（デバイス層）

- 定数追加: `func::APDU = 28`、`m2h::APDU_DONE = 0x10`。
- API 追加（`Vixs` / `Dth30` 層、既存の `reset_card` と並ぶ形）:
  - `apdu_submit(cas: &StreamHandle, apdu: &[u8], tag: u32)` —
    コマンド 28 EXCHANGE を送り、受理（理由コード 0）を確認して返る。
  - `card_query(cas: &StreamHandle) -> (status, Option<atr>)` —
    コマンド 28 QUERY。書き戻しは `CmdResult::payload_fb()` 経由で
    読む（open のハンドル読み戻しと同じ経路が既にある）。
  - 完了の受け: `set_m2h_handler` で APDU_DONE を拾うハンドラを登録し、
    記述子から tag / 完了コード / 応答を読み（fb_read）、待ち手へ渡す。
    ハンドラは現行コードで未使用（§1.3）なので v1 はこれで足りる。
    ただし登録枠は1つしかないため、将来別の用途が要れば
    `stream_message` 型の内部処理へ移すのが拡張路。
- 注意: コマンドは同時実行1つのため、submit の同期応答は速く返る
  設計（§3.2）が前提。`cmd_timeout` は submit には十分だが、完了待ち
  はメッセージ経由なので別に持つ（推奨 10 秒。根拠: ブロック待ち
  1.5 秒 × リトライ + WTX 延長の余裕。超過した場合は「完了紛失」とし、
  遅れて届いた APDU_DONE は tag 不一致として破棄する）。

### 6.2 dth30-backend（セッション層）

- `ensure_cas` / `CasWatch` が CAS を開いてイベントを読む既存の仕組みに、
  APDU の待ち合わせ（tag と oneshot チャネルの対応表）を並べる。
- serve の daemon がデバイスを保持する運用では、USB の claim は
  1プロセスのみなので、APDU の実呼び出しは daemon プロセス内で
  行う形になる（§6.3 の v2）。

### 6.3 dth CLI への露出

- **v1（検証用、one-shot）**: サブコマンド `dth apdu <hex>` を追加する
  （ATR 照会は `dth apdu --atr` または QUERY の同時表示で足りる）。
  tune と同じ直接型で、bring-up → CAS open → リセット → 活性化待ち →
  交換 → 応答を hex で表示、までを1プロセスで行う。§7 の検証は
  この形で実施できる。
- **v2（橋渡し用）**: dth-proto の `Request` に `Apdu` を追加し、
  serve の daemon 経由で叩けるようにする。現行の Request は Stream /
  Status の2種のみで、Reply は Ok / Busy / Error の行ベース。
  APDU 応答は Ok のテキストに hex を載せる形が既存形式に素直に乗る。
- **vsmartcard との接続点**: vicc（仮想スマートカード）のバックエンドは
  serve のソケットへ接続し、Request::Apdu を発行する。これにより
  チューナー運用（daemon がデバイスを保持）とカードリーダー用途が
  同一デバイスで共存する。vicc 側から見た手順は §5 のとおり
  （ATR は QUERY、APDU は EXCHANGE に写像）。

## 7. 検証計画（実装フェーズ）と MMR 突き合わせ

### 7.1 MMR 突き合わせ（我々の配置図 × 彼の card.rs）

`cfw-audit/APDU-DESIGN.md` §2 の表（純正解析由来）と、彼の card.rs の
レジスタ使用を全行突き合わせた。**結果: 全項目一致、相違なし。**

| MMR | 我々の配置図 | 彼の card.rs | 判定 |
|---|---|---|---|
| 0x1020 | bits 15..0 = ETU あたりクロック数 | 同左。加えて初期化で上位に 0xF0000 を書く | 一致（彼の方が完全） |
| 0x1024 | 3007 を書く | `Card::new` で 3007 | 一致 |
| 0x1028 | 送信データ（64 バイト FIFO） | 同左 | 一致 |
| 0x102C | 受信データ | 同左 | 一致 |
| 0x1030 | 0 = idle、0x8100 = ATR 受信、0x800001 \| n<<16 = 送信後受信 | 同左 | 一致 |
| 0x1034 | bits 6..0 = 前回コマンド以降の送受信バイト数 | 同左（`pull` が使用） | 一致 |
| 0x1080 | カードクロック分周（21 → CPU/44） | 21 \| 21<<16（両フィールドに 21） | 一致（彼の方が完全） |
| 0x1084 / 0x108C | ピン機能 / 方向（0x7000 / 0x3000 マスク域） | `pins()` で (v & !0x7800) \| 0x7000、\| 0x3000 | 一致 |
| 0x1088 | bit12 = RST、bit13 = 電源オフ | PIN_RST / PIN_OFF として同左 | 一致 |
| 0x1090 | bit14 = カード挿入 | `detect` で同左 | 一致 |
| 0x1094 / 0x109C | 初期化で 0xFF00 マスク操作 | 0x109C に RMW で 0xFF00 を立て、0x1094 に 0xFF00 を書く | 一致 |

我々の表の不足は2点（0x1020 の上位ビット、0x1080 の第2フィールド）で、
誤りではない。彼の実装が実機で動いていることと合わせ、ハード契約は
二重に裏付けられた状態にある。

### 7.2 実装後の検証手順（合格条件つき）

前提: 実機作業は従来どおり別途承認を取ってから。対象は 検証ホスト の DT-H30。

1. **机上**: 従来手順でビルド（ビルドホスト、armv7 + FW nested build）。
   `dth30-diag fw` で新 FW のベクタ・サイズを確認し、イメージ増加量を
   実測する（§3.5 の見積もりとの照合）。
2. **スモーク（合格条件 = オラクル一致）**: 彼のスタックで bring-up →
   CAS open → リセット → ACTIVATED 確認 → QUERY で ATR が取れること
   （長さと先頭 0x3B のみ確認し、生バイトは保存しない）→ EXCHANGE で
   INITIAL_SETTING (`90 30 00 00 00`) を発行 → APDU_DONE の応答が
   **61 バイト・SW 9000・SHA-256 指紋 8bb4ef99…** と一致すること。
   これは Mode Q が純正 FW + 実カードで実証した応答と同一であり、
   「彼の FW の新経路が同じカードと同じ交換をした」ことの効果側の
   判定になる。指紋が一致しなければ経路のどこかが違う（合格にしない）。
3. **競合の確認**: Program ストリーム視聴中に EXCHANGE を発行し、
   (a) APDU が完了コード 0 で返ること、(b) 復号 TS への影響が
   一過性に留まること、(c) ECM が自己回復して復号が継続すること。
4. **異常系**: (a) カード抜去中に EXCHANGE → 完了コード 1 で
   APDU_DONE が返り、ホストが固まらないこと。(b) 交換中のリセット
   要求 → 完了コード 3。(c) 未活性時の submit → 理由コード 1。
   (d) 61 バイトの APDU → 理由コード 3。(e) 交換中の追加 submit →
   理由コード 2。
5. **復帰**: 従来基準（hw22 replay で純正ブートへ戻し、ハンドシェイク
   5→0、Stage B の TS がベースラインと一致）。

## 8. 未確定点

- **U1**: コマンド 28 / メッセージ 0x10 の純正 FW における意味は未確認
  （純正の ID 表の全域は同定していない）。本設計は彼の FW 上でのみ
  動くため実害はないが、純正ドライバとの併用文脈に持ち込む場合は
  再確認が要る。
- **U2**: MMR 0x1034 のカウンタが本当に mod 128 かは、彼の card.rs の
  記述とコメントが根拠で、127 バイト超の交換の実機実績は彼のコード
  にも我々にもない。v1 の上限（§3.5-2）はこの前提で安全側に取った。
  突破は実機確認つきで v2 とする。
- **U3**: B-CAS の実用 APDU で連結応答（M ビット）が実際に来るかは
  未確認。v1 は完了コード 4 で明示的に落とす。
- **U4**: WTX 延長の累積上限はカード依存で未確定。ECM 遅延の実害は
  §7.2-3 の実測で判定する。
- **U5**: FW イメージの増加量（1–2 KB 級）は見積もり。§7.2-1 で実測する。
- **U6**: ATR 保持バッファ 34 バイトは ISO 上限からの見積もり。彼の
  `parse_atr` は構造を追う方式で長さの上限チェックを持たないため、
  異常に長い ATR の扱い（切り捨て / 無効化）は実装時に決める。
  v1 案は「34 バイトを超えたら未取得（atr_len = 0）として扱う」。

## 9. 実装フェーズの作業分解

### FW 側（crates/dth30-fw）

1. `card.rs`:
   - `Job::Apdu` の追加と APDU 保持バッファ（60 バイト）、tag の保持。
   - `submit_apdu(apdu, tag) -> 理由コード` の新設（ACTIVE ゲート、
     同時実行1つ、キュー満杯の判定を含む）。
   - `send_job` への Apdu 分岐（保持 APDU をそのまま INF として送る）、
     `response` への Apdu 分岐（応答 INF を `apdu_rx` へコピーし
     `Output::ApduDone { tag, code, len }` を発行。M ビット時は
     コード 4）。
   - 中断の伝播: `power_cycle` / `forget` / `activate` がキューを
     消す・上書きする箇所で、保留 APDU への ApduDone 発行。
   - ATR 保持（§5）。
2. `cas.rs`: `Cas::apdu(p, &mut card) -> u32` の新設（ハンドル照合、
   op 分岐、EXCHANGE の投入と理由コード書き戻し、QUERY の同期
   書き戻し）。`card_output` に ApduDone の分岐を追加し、APDU_DONE
   メッセージを組む（メッセージ確保失敗時は保持して再試行、§3.4）。
3. `program.rs`: `card_output` の match に ApduDone の無視分岐を追加
   （Cas 側が Keys 等を無視する既存分岐と対称）。
4. `main.rs`: ディスパッチに `28 => self.cas.apdu(p, &mut self.card)` を追加。
5. `host.rs`: メッセージ ID 定数（APDU_DONE = 0x10）の追加のみで
   済む見込み。

### ホスト側

6. `dth30-core`: func / m2h 定数、`build_apdu_submit` / `build_apdu_query`
   の payload ビルダ、`Vixs::apdu_submit` / `card_query`、APDU_DONE 用
   m2h ハンドラの登録と完了の待ち合わせ。
7. `dth30-backend`: CasWatch と並ぶ APDU 待ち管理（tag ↔ oneshot）。
8. `dth-cli`: `dth apdu` one-shot サブコマンド（v1）。
9. v2（別作業）: `dth-proto` の Request::Apdu、serve 側の処理、
   vsmartcard vicc バックエンド。
