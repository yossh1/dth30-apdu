## 1. 前提 (棄却済み経路は再検討しない)

- 純正 RPCI Func 0x00–0x1A にカード系コマンドは無く、APDU/ATR 素通しは静的解析範囲で
  未発見 (H-002、MED-HIGH) [台帳]。したがって口は「発見」ではなく「後付け」が前提。
- カード情報の返却ブロック経路はホスト側でのみ組み立てられ、デバイス側着地点は無い
  (N-010 正式クローズ) [台帳]。→ §6 のとおり応答チャネルには流用しない。
- MMR 0x1400 台 + byte engine (0x10AC–0x10B8) がカードスロットという説は棄却済み
  (H-005)。byte engine の実体は I2C マスタ [FW Q2]。0x1400 台は CP のバッファ/DMA 系
  ライブラリ (VA 0xA0147224–0xA0149200) で、カードの電気的経路ではない [台帳 §2.2]。
- MMR 直接駆動の無競合説はセッション成立時について棄却済み (H-004) [台帳]。
  → 設計はファーム内部のパッチとして組み、ホストからの MMR 直叩きは採らない。

## 2. カードのハード契約 (確定)

DT-H30 の B-CAS スロットは XCode 2111 内蔵の ISO7816 UART に直結している。
レジスタ契約は [FW2 card.rs] (実機で動く独立実装) が一次情報で、純正ファーム側の
MMR census とも一致する (純正のカードモジュールが触るのは下表のレジスタのみ):

| MMR | 意味 |
|---|---|
| 0x1020 | bits 15..0 = ETU あたりクロック数 (ブロックは CPU クロックで動作)。既定 ETU = 372×44 |
| 0x1024 | ガード/リトライ系 (3007 を書く) [FW2] |
| 0x1028 | 送信データ (64 バイト FIFO、1 書込み = 1 バイト) |
| 0x102C | 受信データ (1 読出し = 1 バイト) |
| 0x1030 | コマンド: 0 = idle、0x8100 = リセットから受信 (ATR)、0x800001 \| (n<<16) = n バイト送信後に受信 |
| 0x1034 | bits 6..0 = 前回コマンド以降の送受信バイト数 |
| 0x1080 | カードクロック分周 (21 → CPU/44) |
| 0x1084/0x108C | ピン機能/方向 (RST・電源ピンは 0x7000/0x3000 マスク域) |
| 0x1088 | ピン出力: bit 12 = RST、bit 13 = 電源オフ |
| 0x1090 | ピン入力: bit 14 = カード挿入 |
| 0x1094/0x109C | 割込み/ピン関連 (初期化で 0xFF00 マスク操作) [FW2] |

プロトコルは **T=1 のみ** (B-CAS カードは TA2 で T=1 を宣言、TA3 = ブロック長が必須)。
手順は 電源投入→RST→ATR→(PPS でレート交渉 or TA2 の特定モード)→S(RESYNCH)→
S(IFS request, 0xFE)→I ブロックで APDU (INITIAL_SETTING = `90 30 00 00 00`、
ECM = `90 34 00 00 Lc <body> Le`)。ブロック応答は最大 ~1.4 秒かかり得る [FW2 card.rs]。

**ホスト側の落とし穴 (設計に取り込む)** [FW2 card.rs guard() の教訓]: MMR 0x1088 は
ホスト側 (純正ドライバ) もランプ/チューナービットの RMW で書き換え、起動直後に
レジスタ全体を1回書く。つまり RST/電源ビットは「書いたら保持される」前提にできず、
ハンドラは使用直前にピンを駆動し直し、保持を仮定しないこと。

## 3. 純正ファームのカード経路 (静的同定)

3層構造である:

1. **CP タスク (APDU の意味層)** — VA 0xA01F7500–0xA01F9600 の文字列クラスタ
   ("CP APDU Length = %d"、APDU 処理本体 xref 0xA01F7734、ECM→DES キー計算
   "CalcDesKeyAB")。MMR を直接触らず、下位層へキュー/メッセージで委ねる [台帳 §2.1]。
2. **カードモジュール (UART + T=1 + ATR)** — **VA 0xA0121000–0xA0127000** (今回同定)。
   根拠: ①MMR 0x1020/0x1028/0x102C/0x1030/0x1034 への直接アクセスがこの範囲に集中
   (0x1028 書込み 0xA01213D4 等、0x1030 書込み 0xA0121478 等)。②ATR/T=1 の指紋が
   中にある (0x3B 比較 ×5、372 ×3、0x8100 ×2、0x90 ×22)。③モジュール内部の jal が
   74 件と自己完結性が高い。外部入口は 0xA0125D5C / 0xA0123E08 (0xA01A6138/0xA01A6150
   から)、0xA0125FE0 / 0xA0124314 (0xA01BA62C/0xA01BA724 から) の4点のみ。
3. **セッション開始パス** — Func 0x19 → 0xA0136C9C。その内部に
   "Initializing CableCard..." の xref (0xA0136D9C/0xA0136DA8) があり、secured
   セッション開始時にカード初期化 (電源・ATR・INIT) が走る [台帳 §2.1、FW SESSION]。

APDU ヘッダ (`90 30` / `90 34`) はイメージ内にデータテンプレートとして存在しない
(全数検索 0 件) → コード内で構築される。CP↔カードモジュール間の委ね機構
(キューか関数呼び出しか、ジョブ投入 API の規約) は**未同定** = 追加調査 #1 (§8)。

[FW2] との対照: みこすのフルファームでもカード層のジョブは Resync/Ifs/Init/Ecm の
4種に限られ、**ホストへの汎用 APDU 素通しは彼も実装していない** (ホストに開くのは
カードリセット要求と状態イベントのみ [FW2 cas.rs])。つまり本設計の口は先行実装の
無い新規設計であり、代わりに彼の card.rs がハード契約と T=1 状態機械の実証済み
リファレンスになる。

## 4. フック設計

### 4.1 採用候補: Func 0x04 (第1候補)

- 到達性: Func < 9 は stage-1 テーブル範囲外でキュー経路に落ち、ワーカーの
  ジャンプテーブル (file 0xFF390) で case へ届く [FW §1.1/§1.3]。
- 現状: テーブル entry (file 0xFF3A0) = 0x80153550 = **DEADC0DE スタブ**。
  スタブは戻らない (DSP キューを回し続けワーカーが止まる) ため、正常運用で
  Func 0x04 が送られれば製品はその時点で壊れる。= 実運用では送られていないはず
  (ただし実証は追加調査 #3)。
- 0x80153550 を指すテーブル entry は **Func 0x04 のものだけ** (0x06/0x07 は
  0x8015362C、0x0A–0x11/0x13–0x18 と ≥0x1B は 0x801537E4) [FW §1.4]。
  → スタブ本体の上書きが他 Func に影響しない。

### 4.2 実装バリアント

- **バリアント A (スタブ本体の上書き、テーブル変更ゼロ)**: スタブ本体
  file 0x53550–0x5361B の **0xCC バイト (51 命令)** がそのままハンドラ置き場になる。
  改変範囲が最小で、課題1で実証した「コード域の改変が実行される」経路と同型。
  収まるのは §5 の Mode Q の薄いシム、または Mode D の入口シム (本体はケーブへ)。
- **バリアント B (テーブル entry の差替え)**: file 0xFF3A0 の4バイトをケーブ内
  ハンドラの VA へ。ケーブ候補 (要・追加調査 #2): ゼロラン file 0x1E238 (6,596 B、
  VA 0x801E238)、file 0x1DC5F (1,163 B)、file 0x1FD10 (1,025 B)。
  **注意**: これらがリンカ上の BSS (実行時にファームがデータとして使う領域) だと
  ハンドラが上書きされる/データを壊す。xrefs census と実機での書込み→再読テストで
  空きを実証してから使うこと。最大のゼロラン file 0xCB18 (69,864 B) はデータ域に
  近く同様の確認が必須で、第1候補にはしない。
- **バリアント C (イメージ末尾への追加セグメント)**: ダウンロードはホスト制御なので
  自前ローダ (replay ハーネス等) なら追加チャンクを送れる。純正 BufFsUSB.sys は
  埋め込みサイズ固定で送れない → 純正ドライバ運用と両立しないため最終手段。

### 4.3 ハンドラ ABI (確定) [FW §1.3 + disasm 実読]

- case 入口で **$s0 = slot の VA** (DDR キャッシュアドレス)。
- 引数オブジェクト: 既存 case は slot+0x14 の非アライン dword (lwl 0x17/lwr 0x14)
  を読み、0x1FFFFFFF でマスクし DDR ベース (gp−0x6C98) を加えて VA 化する。
  本設計はこれを真似ず、**slot 自身のバイト列を入出力に使う** (§6) ため
  ポインタ解決は不要で、シムはさらに薄くなる。
- 復帰: ハンドラは結果を **$v0** に入れ **0xA01537BC へ分岐** する。共通出口が
  slot+0x10 = ($v0==0 ? 1 : 2) を書き、ポスタ 0xA01539CC(slotPhys, slotVA) が
  MMR 0x3048/0x302C でホストへ完了を通知する。成功/失敗の意味論は既存 Func と同一。
- 代替候補フック (優先順位): ② Func 0x06/0x07 (同じスタブ族だが TUNING_NOTES が
  0x05–0x07 を DMA フラッシュ系と推定しており、実ドライバが送る可能性が 0x04 より
  高い) ③ Func 0x16 のワーカー側 entry 差替え (file 0xFF3E8。stage-1 がキューする
  ため到達可能だが、param 形式が I2C 形でホスト側の期待と衝突し得る)。

## 5. ハンドラの処理設計

入力/出力はすべて slot 内 (§6)。処理は2モードを設計し、実装時にどちらか (または
段階的に両方) を選ぶ。

### Mode Q (キュー投入型 — 推奨、要・追加調査 #1)

純正カード層が CP からジョブを受ける内部 API (関数またはキュー) を同定し、
ハンドラは「生 APDU ジョブ」をそこへ投入して完了を待つ。

- 長所: T=1 の送受信シーケンス状態 (ns/nr、レート、IFS) は純正層が一元管理し、
  ECM ジョブとの直列化も層の規約に従う。セッション中でも安全に割り込める
  可能性が最も高い。ハンドラ本体が薄く、バリアント A に収まる見込み。
- 短所: API の存在・規約が未同定。同定できなければ不成立。

### Mode D (直接駆動型 — フォールバック)

ハンドラが [FW2 card.rs] の状態機械を MIPS で再実装し、UART を直接駆動する。
**セッション非アクティブ時に限る** (ゲート条件は §7)。

1. ゲート検査: セッション/カード層が idle でなければ $v0≠0 (失敗) で即帰る。
2. ピン再駆動 (0x1084/0x108C/0x1088、§2 の RMW 教訓)、挿入確認 (0x1090 bit 14)。
3. 電源サイクル → 0x1030=0x8100 で ATR 受信 → ATR 解析 (T=1・TA3 必須を確認)。
4. レート決定 (TA2 特定モードなら TA1 のレート、交渉モードなら PPS)。
5. S(RESYNCH) → S(IFS 0xFE) → I ブロックで要求 APDU を1回交換
   (LRC 検証、R ブロック/WTX 処理、リトライ ≤2)。
6. 応答を slot へ書き、$v0=0 で帰る。カードは電源を落として退出する
   (純正層の次回セッション開始が自前で初期化し直す前提 — Func 0x19 の開始パスが
   毎回カード初期化を行う [§3-3] ため整合する)。

- サイズ見積: 数百バイト〜1KB 超 → バリアント B (ケーブ) が必要。
- ワーカーを最大 ~2 秒ブロックする (T=1 の応答待ち)。その間ほかの RPCI コマンドは
  遅延する。ECM のタイミング処理は CP/カード層側でワーカーとは別タスクのため
  直接は止まらないが、Func 0x0B (番組側入力) 等もワーカー経由であり影響はある。
  実装時は「セッション中に Mode D を使わない」ゲートと合わせて許容範囲とする。
  分割フェーズ化 (開始だけして即帰り、別 Func で回収) は複雑さに見合わず v1 では採らない。

## 6. 引数・戻り値の受け渡し

- **返却ブロック経路は流用しない** (N-010: デバイス側に着地点が無い) [台帳]。
- **slot のバイト列を使う** (確定可能な設計): ホストはコマンド投入時に slot
  イメージ全体を DDR へ書く (replay ハーネス・純正ドライバとも同じ経路) ため、
  slot 内の任意オフセットが双方向チャネルになる。完了後は APER で読み戻せる
  (フェーズ2/課題1で実証済みの読み経路)。先例として Func 0x08 のオープナも
  結果をホスト可読な DDR 領域へ書き戻す [FW Q3.1]。
- レイアウト案 (slot 先頭からのオフセット、slot+0x00–0x13 は既存ヘッダ、
  +0x14 は既存 case のポインタ欄なので避ける):
  - +0x40: u16 要求 APDU 長 (Lc+Le 込みの全バイト数、最大 261)
  - +0x44..: 要求 APDU バイト列 (CLA INS P1 P2 [Lc data] [Le])
  - 応答: +0x40 に u16 応答長を上書き、+0x44.. に応答 APDU (data + SW1 SW2)。
    エラー時は長さ 0 + +0x42 に内部エラーコード (1=カードなし、2=ATR 失敗、
    3=T=1 エラー、4=ビジー/ゲート拒否、5=タイムアウト)。
- ホスト側は通常のポーリング (MMR 0x3048/0x302C のポスタ通知、または slot+0x10 の
  APER 読み) で完了を知り、slot を読み戻す。新規 EP・新規転送経路は不要。

## 7. セッションとの競合・排他

- カードは単一の T=1 チャネル。セッション中は CP/カード層が ECM のたびに
  チャネルを使う (ECM 周期は番組依存で ~0.5–1 秒級)。
- **Mode Q**: 直列化は純正層のジョブ規約に委ねる (ECM ジョブの合間に APDU
  ジョブが1つ入る)。[FW2] の CAS でも「処理中の ECM は差し替え不可、待ち行列の
  ECM は新しいものに置換」という規約があり、同種の規約が純正層にもあるはずで、
  追加調査 #1 で確認する。
- **Mode D**: ゲート必須。ゲートに使える候補: Func 0x08 ディスパッチャが参照する
  "secured context" アクティブ・グローバル [FW Q3.1]、Func 0x19/0x1A の
  セッション状態、カードモジュールの busy フラグ (追加調査 #1/#5 で同定)。
  ゲートが「検査→使用」の競合を完全には閉じない (検査後にセッションが始まる
  窓がある) ため、Mode D の運用規則は「セッションを開く前にだけ使う」
  (カード識別・INIT・状態取得などの定型用途はこれで足りる) とし、セッション中の
  APDU (EMM 受信等) は Mode Q の成立を待つ、を設計上の結論とする。
- どちらのモードでも、ハンドラ実行中にカードが抜かれた場合の扱い (0x1090 bit 14 の
  変化) は T=1 タイムアウトで検出し、エラー 3/5 で帰ること。

## 8. 実装前に必要な追加調査

1. **カード層のジョブ投入 API**: VA 0xA0121000–0xA0127000 の精査。外部入口4点
   (0xA0125D5C / 0xA0123E08 / 0xA0125FE0 / 0xA0124314) の呼出し規約、CP からの
   委ね機構、T=1 状態変数 (ns/nr・レート・busy) の所在、セマフォの有無。
   → Mode Q の成否と Mode D のゲート同定がここで決まる。(机上、緑)
2. **ケーブの空き実証**: ゼロラン候補 (file 0x1E238 等) への lui/addiu 参照 census +
   実機で「純正ブート後にその領域が書き換わっていないか」の読み戻し比較。(机上+実機読取り、緑)
3. **Func 0x04 の非送信確認**: 実 PCastTV セッションの usbmon で Func 0x04
   (および 0x06/0x07) が送られないこと。(観測、緑)
4. **フック機構の決定実験**: テーブル entry (file 0xFF3A0) を既存の固定応答 case
   0x8015361C へ向けるだけの改変で Func 0x04 が「5」を返すか。改変コード実行の
   最小実証であり、ハンドラ実装に先立つ関門。(実機、黃)
5. **複数バイト改変の実績作り**: 課題1は1バイト。ハンドラ規模 (数百バイト) の
   改変イメージでのブート+読み戻し一致を段階的に確認する。(実機、黃)

## 9. 承認ポイント (ゾーン)

- 追加調査 #1–#3: 読み取り・観測のみ = **緑**。
- 追加調査 #4・#5 と、将来のハンドラ実装・投入: DDR 上の揮発イメージ改変であり
  USB リセット/純正再ブートで完全復旧する = **黃** (実行してよいが会話に明記)。
  本機にフラッシュ書換え経路は無く (ファームは毎回 DDR ダウンロード)、
  **赤**に相当する操作はこの設計には存在しない。
- みこす CFW (dth30-fw) そのものの投入は本設計の範囲外 (別途承認が必要)。
- 純正ドライバ (Windows/PCastTV) との併用運用に進む場合は、ホスト側ツールの
  投入方法 (自前ローダ) が別途必要になる — それも黃。

## 10. 判定の要旨

- フック (Func 0x04、スタブ上書き or entry 差替え) と ABI は静的に確定し、
  課題1で「改変コードが実行される」ことまで実機で実証済み。
- カードのハード契約と T=1 手順は実証済みリファレンス [FW2] で完全に分かる。
- したがって残る不確実性は機構ではなく工学量 (純正層 API の同定、ケーブ実証、
  改変サイズの段階確認) であり、**設計としては成立する**。推奨する実装順序は
  #4 (フック実証) → #1 (Mode Q の可否判定) → Mode Q 優先、不可なら Mode D。
