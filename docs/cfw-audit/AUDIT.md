# CFW 監査フェーズ1（静的）— DT-H30/U2 ファームイメージ検証の有無

調査日: 2026-11-22。範囲: 静的解析と読み取りのみ（改変イメージの作成・投入はしていない）。
材料: `~/workspace/dth30-re/xcode2emb_embedded.bin`（純正イメージ）、`~/workspace/dth30-re/INIT_SEQUENCE.md`（純正ドライバ精査、既存成果）、本ディレクトリに clone した `driver/`（i4M1k0SU/DTH10-series-driver、dth30-core / dth30-fw を含む）、`parse_image.py` / `parse_image_out.txt`（本監査のパース結果）。

## 1. イメージ形式の構造

- 全体: **raw・ヘッダレスの MIPS LE メモリイメージ**。リンク先は SDRAM phys 0x100000（KSEG0 0x80100000 / KSEG1 0xA0100000）。長さ 0x126F90 = 1,208,208 バイト（16 の倍数）。末尾にトレーラ／チェックサムブロックはない（最終ワード群はデータテーブル、末尾は 0 パディング）。
- ヘッダ頁（file 0x000–、DDR phys 0x100000– に載る）:
  - `+0x000`: リセットスタブ（nop、`lui s5,0xa000`、分岐）。コア解放後、DDR 0 のトランポリン（下記ベクタ entry 0）経由でここに入る。
  - `+0x100`: 0x00000301、`+0x104`: 0x00000003（意味は未同定。みこす CFW は同位置に magic "DTH3" と version を置く。どちらのローダもこの2ワードを読まない）。
  - `+0x110`: ベクタテーブル件数 = **6**。
  - `+0x120`–`+0x17F`: ベクタエントリ ×6、各 16 バイト {dst, w1, w2, w3}。dst ∈ {0, 0x180, 0x200, 0x380, 0x400, 0x480}（SDRAM window 0 の例外ベクタ位置）。w1..w3 は `lui/ori/jr` のトランポリン命令語で、飛び先はイメージ内同オフセット（0xA0100000+dst）。ローダは w1..w3 を dst+4/+8/+12 へ書き、dst+0 を最後に 0 クリアする。
  - `+0x180`–`+0x4FF`: 例外スタブ本体（各ベクタ位置）とゼロパディング。+0x180 のスタブはリセット実体（file 0xF8AE8 相当）への入口を含む。
  - `+0x520`–`+0x57F`: 致命的エラーレコード領域（ランタイムにファームが書く。みこす CFW の boot.rs の FATAL_AREA 0x520..0x580 と一致）。
- 本体: RTOS イメージ。コマンド処理系 file 0x52000–0x55000、フロントエンド 0x31000–0x3E000、ストリームライブラリ 0xA0000–0xB3000、DSP 係数テーブル 0x100000 以降。
- イメージ内には CableCARD/OpenCable CP スタックと証明書群（POD_CERT_* 文字列、CableLabs CA 証明書、"VIXSCONFIDENTIAL" 等）が 0xFE000–0x126F90 付近に存在する。**これはファームが CableCARD を認証するためのライブラリであり、イメージ自身の検証とは無関係**（後で混同しないこと）。
- **チェックサム／署名フィールド: なし**（本監査のパース＋候補照合の範囲。照合内容: CRC32／dword 加算／dword XOR を {全体, 0x200 以降, 0x1000 以降, 先頭 1MB} について計算し、ヘッダ 0x000–0x1FF と末尾 0x100 バイトの全 dword と突合 → ヒットなし。CRC32 テーブル（0x77073096〜）もイメージ内に存在しない）。

## 2. ドライバ側ロード経路の監査

### 純正 BufFsUSB.sys（INIT_SEQUENCE.md §2.2/§2.3/§5 の既存精査に基づく）
- `InitializeMipsNonSecured`（名称どおり非セキュア経路）→ `Down_Load_Embedded_Mips_Prog` が、.data 埋め込みイメージ（VA 0x51058、長さは直後の dword VA 0x177FE8 = 0x126F90）を ≤1MB チャンクで BAR1 アパーチャ＋MMR 0x43C ページングにより DDR phys 0x100000 へ**生コピー**する。
- **検証値の計算・付加・送信は一切なし**。転送完了の確認は NcUrb ステータスと転送バイト数のみ。ダウンロード後にベクタテーブルを SDRAM から読み戻して window 0 へ転記し、FB パラメータ（0x40 電源モード／0x44 クロック／0x48 メモリサイズ／0x4C 有効=1）を書く。0x44 の読み戻し照合は SDRAM の書込み可否テストであり、イメージ内容の照合ではない。
- その後 MMR 0x30F8 でコア解放し、ファーム自身が発行する状態（MMR 0x3028: 5=ALLOC_FB → 0=OK、7=INIT_FAILED）を待つ。INIT_FAILED はファーム側の初期化失敗申告であり、検証の合否ではない（みこす CFW の host.rs も同じ状態を自ら書く）。

### みこす DTH10-series-driver（dth30-core、本監査で精読）
- `vixs/mips.rs::start` が純正経路を access-for-access で再現（NET2280 DMA、window n+1 へチャンク転送）。**イメージ本体の読み戻し照合なし**。あるのはベクタ件数 ≠ 0xFFFFFFFF のチェックと FB 書込みテストのみ。
- `vixs/firmware.rs` の SHA-256 照合は**ホスト側ポリシー**（純正イメージの取り違え防止）で、チップへは送られない。自作イメージ（`crates/dth30-fw`）は +0x100 の magic とベクタテーブルの健全性だけで受理され、内容はビルドごとに変わる（ハッシュ固定なし）。`build.rs` が自作ファームをビルドしてドライバに組み込む。
- プロジェクト既存の記録 replay（hw1/hw22 の Stage A）は純正列の再生であり、チェックサム op を含まない（INIT_SEQUENCE §2.4 の最小ブート列が根拠）。

## 3. イメージ検証の有無 — 判定

- **署名検証: 存在しない（確度 HIGH）**。根拠の複合: (a) 両ローダの全経路に検証値の計算・送信がない、(b) イメージ形式に署名フィールドがない、(c) コア解放後の最初の実行はホストが DDR 0 に書いたトランポリンであり、ブート経路に ROM が介在する段がない、(d) 内容・長さとも純正と異なる自作イメージ（みこす CFW）が実機で動作した実績がある。
- **チェックサム: 存在しない（確度 HIGH、§1 の照合範囲）**。ホスト→チップの送信なし、イメージ内フィールドなし。ファーム自己検証は「期待値を保持するフィールドが存在しない」以上成立しない（CRC32 テーブルも不在）。イメージ内の証明書検証コードは CableCARD 用で対象が異なる。
- チップには融合鍵＋変換エンジンがある（OTP 署名＝機器同一性、コマンド 27）が、両ファームとも起動時のイメージ照合には使っていない（ランタイムサービス）。
- **「検証コードが見つからない」と「存在しない」の区別**: ホスト側とイメージ形式については「存在しない」と言える根拠が揃った。チップ内蔵 ROM については未ダンプで直接観測がないため、その部分の棄却は効果側の間接証拠（上記 (c)(d)）による。残留留保: (1) みこすの DT-H30/U2 動作は本人の X 投稿（2026-11-22）と公開コードによる他者実績で、うちの再現ではない（彼の README の確認機種は DT-H50/U2、ローダ経路の access 照合も DT-H50/U2）。(2) うちの個体の USB PID は 0411:0128 と確認済み（2026-11-22、検証ホスト の lsusb で観測。みこすの DT-H30 検証 PID 0x0128 と一致）。フェーズ2 で自前の効果側証拠に格上げする。

## 4. フェーズ2 決定実験の設計案（未実施・要ユーザー承認）

- **変更バイト（第1候補）**: file offset **0x11BB8B** の 'V' (0x56) → 'W' (0x57)。"ViXS AAC encode" 文字列の先頭で、DSP テーブル域（file 0x100000 以降）のデータ内文字列。実行コードではなく、ブート／ハンドシェイク／TS のいずれにも関与しない。代替候補: file 0x1C0 の 0x00 → 0x01（例外スタブ間のゼロパディング）。
- **投入手順**: 既存の hw22 系 Stage A replay をそのまま使い、イメージだけを差し替える。検証ホスト 上で原本のコピーを作り 1 バイトだけ書き換え、改変前後の SHA-256 を記録する。手順の骨格（USB リセット→DDR 初期化→ダウンロード→ベクタ転記→FB パラメータ→コア解放）は純正列と同一にし、既存の注意事項（再接続時に set_configuration を呼ばない、MMR 0x58 bit2 と Func 0x19 を手順に含めない）を継承する。実験は現在 検証ホスト で起動中の純正ファームのブートを置き換えるため、開始前に現行セッションを止め、終了後は純正イメージで再ブートして通常運用（セッション＋TS）に戻す。
- **効果側の観測**:
  1. ダウンロード直後・コア解放前に APER で SDRAM phys 0x100000+0x11BB8B を読み、変更バイト 0x57 が実在することを確認する（改変イメージが実際に載ったことの証拠）。【2026-11-22 フェーズ2実施時の訂正】この phys 表記は実読み戻しの座標としては誤り。実際は aperture field 2 の全域ダンプ（ペイロード窓先頭 0x1B960、対象バイトは窓 offset 11）を取得し、送信ペイロードとの全域 diff 0 と対象バイトの値で確認した。観測①の目的（解放前に改変イメージの搭載を効果側で確認）はこの形で設計どおり達成されている。
  2. ハンドシェイク: FB+0x20 の安定読み成立、MMR 0x3028 が 5 (ALLOC_FB) を 3 回 → ACK → 0 (OK)。7 (INIT_FAILED) や 100 tick タイムアウトは失敗側。
  3. 既存 Stage B（セッション開始＋ch27 選局）で TS 10 秒・同期 100%、スクランブル率が純正対照 run と同等であること。
  4. **A/B/A 構成**: 直前に純正イメージで対照 run（同一手順で正常ブートを確認）→ 改変 run → 異常時は純正で再 run し、ハーネス健全性と分離する。
- **棄却条件**: 改変 run でのみハンドシェイク失敗／state 7／TS 不通が発生し、A/B/A で再現性が分離できれば「イメージ依存の拒否あり（検証または構造チェック）」として §3 の判定を差し戻す。改変 run が全観測を通過すれば「検証なし」が自前の効果側証拠で confirmed になる。
- **リスク**: イメージは DDR 上のみ（揮発性）。失敗しても USB リセット／電源断で復旧し、恒久的な書換えは発生しない。

## 5. 仮説の判定と次の一手

- 仮説: ホスト側ドライバ（純正・みこす版とも）はイメージの検証値を計算してチップへ送る ／棄却条件: 両ローダの全経路精読で検証値の計算・送信が一切見つからなければ棄却 → **rejected**。根拠: §2（みこす版の SHA-256 はホスト内ポリシー照合のみ）。
- 仮説: イメージ形式にチェックサム／署名フィールドが存在する ／棄却条件: ヘッダ・末尾のパースと候補チェックサム照合の結果、該当フィールドが同定できなければ棄却 → **rejected**（§1 の照合範囲）。根拠: parse_image_out.txt。
- 仮説: ファーム自身が起動時に自己イメージを検証する ／棄却条件: 期待値フィールドと検証コードの双方が同定できなければ棄却 → **rejected**。根拠: 期待値フィールドなし＋CRC32 テーブルなし。イメージ内の証明書検証は CableCARD 対象。
- 仮説: チップ／ブート ROM が署名検証を行い、改変イメージを弾く ／棄却条件: 純正と異なる内容・長さのイメージが実機で起動・動作する → **rejected（他者実績による。フェーズ2 で自前再現して確定させる）**。根拠: みこす CFW の公開コードと実機動作（DT-H50/U2 は README、DT-H30/U2 は 2026-11-22 の X 投稿）。
- 次: フェーズ2 の承認取り（上記 §4 の設計、変更は 1 バイト、投入は既存 Stage A replay のイメージ差し替えのみ）。うちの個体の USB PID は 0411:0128 と確認済み（2026-11-22、検証ホスト の lsusb。みこすの検証 PID と一致）で、実施前条件は満たされている。
