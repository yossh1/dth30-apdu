## 1. N-052: Mode Q ハンドラが流用すべき ctx

### 1.1 前提の訂正（仮説の棄却）

**仮説 N52b「0xA012BC70 はチャネルオブジェクトのオープナである」を rejected。**
根拠: 0xA012BC70 は関数エントリではなく、関数 **0xA012B7C8** の末尾に置かれた
共有リターンブロック（`move $v0,$zero`＋復帰列）である。0xA012B7C8 本体は
0xBC バイトレコードを走査して 0xA014xxxx バッファライブラリ
（0xA0146E58／0xA0147338）を呼ぶストリーム系スキャナで、POD チャネル
オブジェクトの生成とは無関係。N044-JOB-API.md §6 項目3 の
「+0x64→サブオブジェクト」という読みは再現できなかった（同関数は
+0x64 フィールドを ctx 的に触らない）。

カードモジュール初期化 **0xA012B074** が生成するものも ctx ではない:
T=1 状態構造体（静的 @0x80237FE8、ポインタ大域 0x802370E0）と、
キー 0xD で登録されるセッションオブジェクト（@0x80240AA0、
登録 0xA018361C）だけである。

### 1.2 ctx の実体（確定・HIGH）

ジョブ投入 API 0xA0121700 の第1引数 ctx の実体は **POD（CableCARD）
チャネルオブジェクト**である:

- 静的 BSS オブジェクト（VA 域 0x8025xxxx）、サイズ 0x2718 バイト以上。
  ホスト記述子の中ではそのアドレス（物理形）で識別される（§1.3）。
- ノードは +0x00 をリンクとして循環リストにつながれ、アンカは
  **0x80255158**（根拠: 状態機械 0xA0124F7C の `lui $v0,0x8025 /
  addiu 0x5158`、カードリセット関数 0xA012593C のリスト走査、
  タイムアウト経路 0xA0124724 の `lw *(0x80255158)`）。
- リストへの挿入ストアは 0xA0189380（0xA018 オブジェクトライブラリ内）。
  ノード生成関数の一点特定には至らなかった（POD チャネル開設時に
  同ライブラリ経由で生成される。ここは未分離として残す）。

ctx のフィールド（今回新たに読めた分）:

| offset | 意味 | 根拠 |
|---|---|---|
| +0x00 | リストリンク | 走査各所 |
| +0x14 | 有効フラグ（≠0 で処理対象） | 0xA0124F8C |
| +0x18/+0x1C | 書戻し desc の +0x00/+0x04 のコピー元 | 0xA0123F08 |
| +0x30 | フラグ。**bit 0x10 = カード参加チャネル** | カードリセット関数自身の判定 0xA012594C–5954 |
| +0x3C | チャネル番号（イベント ID = (chan<<2)+0x341） | 0xA0123F08 |
| +0x374 | 状態フラグの影（state+0x118 と比較される） | 0xA0125958 |
| +0x378 | トランザクション領域 0x2390 B（ホストのレコードがコピーされる） | ディスパッチャ 0xA01A5EE0 |
| +0x2714 | 通知／活性化要求フラグ | §1.4 |

### 1.3 純正経路で ctx がどう渡るか（確定・HIGH）

- 汎用ディスパッチャ **0xA01A5EE0** がホスト記述子の先頭 dword から
  ctx を導出（マスク 0x1FFFFFFF＋DDR 基底）し、レコード +0x1BC の
  フラグで振り分ける: bit0 → 活性化コンストラクタ **0xA0125D5C(ctx)**、
  bit1 → **0xA0123E08(ctx)**、bit2 → 投入ラッパ **0xA012BE14(ctx)**。
  あわせてホストのレコードを ctx+0x378 へコピーする。
- POD パーサ **0xA01262CC** は呼び出し連鎖（0xA0129924 経由）から
  ctx を $a0 で受け取り、投入呼び出し 0xA01263FC／0xA01265C4 へ渡す。
- **実効参照は job+0x18 ではなく req+0x8C**（N-049 の訂正を裏付け）:
  活性化コンストラクタ 0xA0125D5C は job+0x18 = 0 にするのに同じ
  状態機械で完走する。リクエスト構築側は全て req+0x8C = ctx を書く
  （0xA0125D5C、充填 0xA0123210／0xA0123398、充填 0xA0122C9C）。
  状態機械の通知も 0xA0123F08(req+0x8C, code) で、コールバックも
  ctx = req+0x8C を受け取る。

### 1.4 ハンドラの手本になる投入ラッパ（確定・HIGH）

**0xA012BE14(ctx)** は Mode Q と同形の完成した投入手順である:
state+0x118 bit1（ATR 解析済み）でゲートし、リクエストを確保して
充填 **0xA0122C9C(req, ctx)**（固定 APDU `90 32 00 00 00` を req+0x80 へ、
長さ 5 を +0x84、種別 0 を +0x88、ctx を +0x8C）で組み立て、
**0xA0121700(ctx, req, aux=0xA013BD58)**（完了コールバックは
0xA013 ライブラリ側）で投入し、失敗時に req を解放する。
カード未準備時は ctx+0x2714 = 1 を立てて戻る（+0x2714 は状態機械の
リスト走査が消費し、0xA0123F08(ctx, 1) を呼んでクリアする。
走査コード 0xA0124FC4–0xA0124FF0）。

### 1.5 結論: 流用すべき ctx と選択方法

**確定: 流用先は 0x80255158 リスト内の「+0x30 bit 0x10 が立ったノード」**
（カード参加チャネルの ctx）。選択方法はファーム自身の流儀どおり
リストを走査して該当ノードを取る（状態機械とカードリセット関数が
実際にそうしている）。複数該当する場合は +0x3C のチャネル番号で
セッションのチャネルと照合する。
確度: 選択機構そのものは **HIGH**。bit 0x10 ノードの一意性は実行時の
性質で静的には数え切れないため **MED**（推測を含む）。一意性の実測は、
セッション確立後に APER でリストを読む実機読み取り（緑）で可能だが
今回の机上範囲には含めない。

ハンドラの必要フィールドがこの候補で満たされるかの確認:
- 書戻し先 desc は ctx 内にはない。0xA0123F08 がレジストリ検索
  0xA0153A38 で **キー 0xF** の desc を引く。ctx から要るのは
  +0x18/+0x1C（desc+0x00/+0x04 のコピー元）とコード（desc+0x20）と
  +0x378 領域内の各フィールド（+0x418/+0x424/+0x430、条件つきで
  +0x548/+0x5CC。いずれもコピー済み領域の内側:
  0x378+0x2390 = 0x2708 > 0x64C）。→ 候補は純正経路が使うのと
  同一のオブジェクトなので、**構成上満たされる**（確定・HIGH）。
- ハンドラ側は 0xA012BE14 を雛形に、充填（自分の APDU）と
  コールバック（自前）を差し替える形が最短である。

## 2. N-046: 純正ホスト側は Func 0x04 を送らないか

### 2.1 方法

ドアベル MMR 0x3020 への書込み箇所は BufFsUSB.sys 全体で 2 箇所だけ
（census [C]、n052/n046_func_census_out.txt）:

1. 汎用送信関数 **0x1a0bc** 内（0x1a325）: 書く値は [req+0x18]
   （同関数が slot+0xC へも同じ値を書く、0x1a17d–0x1a188 実読）。
2. 特殊経路の関数 **0x3df56**（0x3dfc5）: 値は即値 **0x1B** 固定
   （0x3dfc3 `push $0x1b` 実読。ファーム側 §1.1 の Func 0x1B 特別扱いに一致）。

よって発行 Func の全集合は「0x1a0bc の全呼び出しで [handle+0x18] に
入る値」＋ {0x1B} に帰着する。全 22 呼び出しを解決した（census [A][D]）:
21 件は即値ストアで確定、残り 1 件（0x1a538、完了ハンドラ 0x1a388 内）は
in-flight キューから取り出した既製ハンドルの再送で、新しい値は
生まれない（census 出力 [E] に実読根拠を追記済み）。census [B] に
現れる NcRpci ライブラリ関数群（0x12f4c 等）の +0x18 ストアは
別構造体のエラーコードフィールドであり送信ハンドルではない
（同 [E]）。

BufFsUMe.sys には 0x3020 参照が一切ない（ドアベルを書かない）。
ユーザー側コンポーネントはドアベルを直接書けずドライバ経由であり、
[handle+0x18] を引数や IOCTL バッファから入れる経路はドライバ内に
存在しない（全発行元が即値）。

### 2.2 結果（確定・HIGH）

純正スタック（BufFsUSB.sys）が発行する Func の全集合:

**{0x08, 0x09, 0x0A, 0x0B, 0x0D, 0x10, 0x12, 0x13, 0x14, 0x15, 0x16,
0x18, 0x19, 0x1A, 0x1B}**

発行元の対応は census [D] のとおり（例: 0x08 は選局系 6 関数、
0x1B は 0x3df56）。**Func 0x04 は含まれない**。設計 §3 の関心対象である
0x06／0x07 も含まれない。

### 2.3 残る留保（無理に確定しない部分）

- 静的解析の性質上、計算された間接値で Func フィールドを入れる経路を
  100% は排除できない。ただし全発行元の実読では証拠は皆無であり、
  上記の確度 HIGH は「出荷ドライバ内に Func 0x04 を発行するコード
  経路は存在しない」という形で置く。
- 間接証拠の強さ: Func 0x04 のスタブ本体は DEADC0DE を置いて自己
  ループする（戻らない）。純正スタックが通常運用で送ればワーカーが
  止まり純正環境がハングするはずで、出荷製品でそれは成り立たない。
- 効果側の動的確認（実 PCastTV での USB キャプチャ）は未実施。
  やる場合に必要なもの（**要ユーザー環境**）: Windows 実機＋PCastTV
  導入済み環境と DT-H30 本体、USBPcap 等での当該デバイスの USB
  キャプチャ、通常運用（選局・録画・EPG 取得）を一巡させ、
  MMR 0x3020 への書込み値（＝slot+0xC の値）に 0x04 が現れないことを
  観測する。設計の前提としては本節の静的確定で足り、動的確認は
  残件として残す（ブロッカーではない）。
