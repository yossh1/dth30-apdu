## 0. 仮説と判定（要約）

- 仮説N49: 0xA0123F08 はキー 0xF の DDR デスクリプタへ ctx フィールド＋コードを書き戻す所有者通知であり、応答データの最終段はこの書戻しか POD 側の状態構造体直接読みのどちらか ／棄却条件: 0xA0123F08 本体にデスクリプタへのストアが無い、または応答コピーが全く別の関数で完結している場合
  → **confirmed（形を精緻化）**。0xA0123F08 はキー 0xF デスクリプタへの書戻しで確定（§1.1）。ただし応答データの最終段は 0xA0123F08 ではなく、**ジョブ完了コールバック（job+0x2C = aux）が状態 RX バッファをその場で解釈し、デスクリプタ／チャネル層へ渡す**経路だった（§1.2）。
- **N044-JOB-API.md §3 の訂正**: 同書は「コールバックはない（確度 MED-HIGH）」としたが、これは**誤り**。投入 API の第3引数 aux は完了コールバック関数ポインタで、ステートマシンが受信完了時に `jalr (job+0x2C)`（$a0=0、$a1=req）で呼ぶ（0xA01248AC、§1.2）。POD 経路（0xA01262CC）は aux に 0x80122D5C／0x8012328C を渡している。コンストラクタ経路（0xA0125D5C）は aux=0 のため N-044 の観測範囲では見えなかった。
- 仮説N50: alloc 0xA01548D4 はクラス表を持つ固定サイズ・クラス制アロケータで、クラスからペイロード上限が決まる ／棄却条件: クラス表が無く単一プールのフリーリストである場合
  → **rejected（形を変えて）**。クラス表は存在せず、単一の固定ブロックプール（プールオブジェクト @phys 0x23F364、global 0x8023709C）のフリーリスト pop/push だった（§2）。ペイロード上限はクラスではなくリクエストオブジェクトの構造（インライン 0x80 B）で決まる。
- 仮説N51: NS/NR の明示リセットは 0xA0124210 の中にある ／棄却条件: 0xA0124210 本体に状態 +0x110/+0x114 へのストアが無い場合
  → **rejected**。0xA0124210 はキューのパージ（全ジョブ取外し＋未処理ジョブの所有者へコード1通知＋解放）で、NS/NR には触れない。実リセット箇所は別途同定した（§3）。
- 仮説N45: ゼロラン候補（file 0x1E238 等）はイメージ内の実在の空きで、BSS でも他用途でもない ／棄却条件: 候補への参照・書込みが見つかる、またはロード範囲外である場合
  → **候補により分岐**。file 0x1E238（6,596 B）のみ棄却条件を免れた（参照皆無・ロード範囲内）。file 0x1DC5F と 0x1FD10 は**スタック／エントリ領域で使用中**、file 0xCB18 は**参照多数のデータ領域**で、いずれも rejected（§4）。

## 1. N-049 応答回収側の確定

### 1.1 0xA0123F08 本体（確度 HIGH）— キー 0xF デスクリプタ書戻し

引数: $a0 = ctx、$a1 = コード。呼出し元9件（0xA01242C8、0xA01243BC、0xA01245C8、0xA0124680、0xA01248F8、0xA0124D74、0xA0124F34、0xA0124FDC、0xA012BD88）。

動作（func_3f08_4314.asm）:
1. カウンタ（$gp-0x7F3C）を +1 し、検索関数 0xA0153A38（キー 0xF）で登録デスクリプタを得る。無ければ即 0 復帰。
2. デスクリプタ +0x14 の phys アドレスを DDR ベース（global $gp-0x6C98）で VA 化し、次を書き戻す:
   - desc+0x00 = ctx+0x18、desc+0x04 = ctx+0x1C
   - desc+0x08 = *(ctx+0x378+0xA0)、desc+0x1C = *(ctx+0x378+0xAC)
   - **desc+0x20 = コード引数**
   - desc+0x24 = *(ctx+0x378+0xB8)
   - 条件付き（上記 desc+0x24 の元値（ctx+0x430）の bit 0x20 が立つ場合のみ）: desc+0x1AC = *(ctx+0x378+0x250)、**ctx+0x548..0x5C8 の 0x80 B を desc+0x12C..0x1AC へコピー**、desc+0x230 = *(ctx+0x378+0x2D4)、**ctx+0x5CC..0x64C の 0x80 B を desc+0x1B0..0x230 へコピー**、最後に desc+0x20 = 0 に戻す。
   - デスクリプタの必要サイズは 0x234 以上。
3. 活動トレース（0xA0100540 域）を打ち、0xA01538B0（phys(ctx), キー 0xF, デスクリプタ, 0）で登録を解除/更新（成功までリトライ）。

つまり 0xA0123F08 は「ctx の状態スナップショット＋通知コードを、キー 0xF のホスト可視デスクリプタへ発行する」関数で、N-044 の本命推定（確度 MED）は**確定（HIGH）**に上がる。イベント ID 0x3C2/0x3C3 は本関数とは無関係で、ステートマシンの ATR 完了処理（0xA0124CF8 付近）が別途発行するもの（N-044 §3 の並記は混同気味だったので分離する）。

このデスクリプタが、ホストドライバが「返却ブロック」を組み立てる際のデバイス側の発行源の一つと整合する（N-010 の「ブロックはホスト側でのみ組み立てられる」と矛盾しない）。

### 1.2 応答データの最終段（確度 HIGH）— 完了コールバックが RX バッファをその場で読む

ステートマシン 0xA0124314 の受信完了処理（0xA0124860–0xA01248D8、nsnr_sm_ctx.asm）:
- 状態+0x134 ← 状態+0x130（受信長を確定）。
- 先頭ジョブについて、**job+0x10 bit0 == 0 かつ job+0x2C（aux）!= 0 なら `jalr aux`（$a0=0、$a1=req）を呼ぶ**（0xA01248AC）。これが完了コールバック。
- その後ジョブを取外し（0xA0182708）て解放し、戻り値（次ジョブ）があれば即 0xA0121264 で交換を続ける。

POD 側コールバックの実例（callbacks_fill.asm）:
- **0xA0122D5C**（tag 0x84 経路＝INS 0x36 系ジョブの aux）: 状態 RX バッファのバイト +5..+8（16bit 値×2）を読み、キー 0xC のデスクリプタへ状態ブロックとして書き戻す（desc+0x1BC／+0x1C0 にその値、+0x30 = 0x80001 等）。値が 0x100 の場合は後続ジョブを組み立てて 0xA0121700（ctx, req, aux=0x80122BB8）で連鎖投入する。
- **0xA012328C**（tag 0x85 経路＝INS 0x38 系ジョブの aux）: 状態+1 の bit 0x20（エラー表示）と状態+2 を検査し、**応答データを状態 RX バッファ +9 から（状態+4 の値 −4）バイト分、新規 pool オブジェクトへ memcpy（0xA01FE8A0）して、0xA0121918（チャネルオブジェクト, obj, 長, obj）でチャネル層へ引き渡す**。

したがって応答の流れは「状態 RX バッファ → （コールバックがその場で解釈・必要分だけコピー） → デスクリプタ（キー 0xC/0xF）またはチャネル層 0xA0121918 → ホスト」であり、**カードモジュールから POD バッファへの一括コピーは存在しない**。N-044 §3 の候補2（POD 側が状態構造体を直接読む）が実態に近く、読み手はコールバックである。

### 1.3 0xA01262CC の正体（確度 HIGH）— 受信処理ではなく POD 側の投入側パーサ

呼出し元は POD ライブラリ 0xA0129924 の1件。入力バッファ（$a1、長さ $a2）のタグ付きレコード列を解析する:
- タグ 0x84: 8バイトエントリ列。各エントリの ID ペアを状態+0x148/+0x14C、第2ペアを状態+0x150/+0x154 と照合し、一致したら request を alloc し 0xA0123210 で APDU を構築（**`90 36 00 00 Lc <data> 00`**、req+0x80 = 0x36、+0x84 = Lc+6、+0x88 = 0）して 0xA0121700（ctx, req, **aux=0x80122D5C**）へ投入。
- タグ 0x85: 16bit 長つきエントリ列。同様に照合し、0xA0123398 で APDU を構築（**`90 38 00 00 <Lc=長+9> <ヘッダ6Bコピー> <data> 00`**、req+0x80 = 0x38、+0x84 = 長+0xF、+0x88 = 0）して 0xA0121700（ctx, req, **aux=0x8012328C**）へ投入。データが長い場合は**状態+0x12C を上限として複数 request に分割**し、残量が尽きるまでループする（0xA01265F4）。
- その他のタグ: チャネルオブジェクト（ctx+0x8000 の表）の状態で分岐し 0xA0121918 へ回す。

状態+0x12C の書き手は census で3件のみ: 活性化時のゼロクリア×2（§3）と、応答処理関数 0xA0121F00 内の 0xA0121F48（受信データのバイト（状態+0x12）を +0x12C へ格納）。すなわち +0x12C はカード応答（ATR/INIT 応答域）由来のバイト値で、分割上限として使われる（IFSD 相当という解釈は推測・MED）。

### 1.4 リスト操作関数 0xA0181FCC／0xA0182708 本体（確度 HIGH）— fact ①の確度引き上げ

両本体を読んだ（list_ops.asm、list_remove.asm、list_attach_tail.asm）:
- 0xA0181FCC（登録）: ジョブを所有者の侵入型リストへ挿入する。リンクは **job+0x00 = 前方向／job+0x04 = 後方向の双方向リンク**と、**job+0x1C／+0x20 ↔ 所有者 +0xC アンカー**の第2リンク対、さらに所有者のスロット表（所有者+0x1C + 4×idx、idx = job+0x14、タグ 0x100/0x101/0x102 を job+0x0C へ書く）への登録を伴う。戻り値: 所有者（セッション）+0x10 != 0 の場合は 0（キューイングのみ）、そうでない場合は投入したジョブ自身（または先行ジョブ）を返し、投入 API 0xA0121700 は非0なら即 0xA0121264 で交換を開始する（submit_api.asm 0xA01217A8–0xA01217B4）。
- 0xA0182708（取外し）: 両リンク対を外し（0xA0182A38 の unlink）、所有者スロット表の該当エントリを 0 クリアしタグビットを落として、**次のジョブ（無ければ 0）を返す**。呼出し側（ステートマシン 0xA0124A80、パージ 0xA0124258）は戻り値を次に交換するジョブとして使う。
- 結論: N-044 の fact ①「セッションオブジェクトの単一リンクリストへ登録」は、**キューが単一である点は正しく、確度は HIGH に上がる**。ただしリンク自体は単方向ではなく双方向（+0x00/+0x04）＋所有者アンカー対（+0x1C/+0x20）の複合構造である（文面の「単一リンクリスト」を「単一のキュー（双方向リンク）」と読み替えるのが正確）。

### 1.5 0xA0124210 の正体（確度 HIGH）

呼出し元はステートマシン内の2件（0xA0124508、0xA0124F3C）のみ。動作: セッションのジョブリストを先頭から全て取り外し、各ジョブについて req+0x80 == −1（未処理）なら所有者へ 0xA0123F08（req+0x8C, 1）を通知し、ジョブ記述子と request を free（0xA0154C9C）する。**キューの一括パージ**（活性化失敗時等の後始末）であり、NS/NR には触れない。

## 2. N-050 ペイロード上限の確定

### 2.1 alloc 0xA01548D4 の実像（確度 HIGH）

クラス表は無い。$a0 = プールオブジェクトへのポインタで、そのプールのセマフォ（global $gp-0x6AC0）を取り、フリーリスト先頭を pop する汎用プールである（alloc.asm）。ブロックにはマジック（free 状態 0xF2EEF2EE、確保時プール 0x8023709C では 0x5000F2EE を +0x0C へ）が使われる。free は 0xA0154C9C。

- ジョブ記述子も request オブジェクトも**同一プール**（global 0x8023709C が指すプールオブジェクト @phys 0x23F364、初期化関数 0xA01524A4 が DDR サイズ検出から配置を決める。pool_init.asm）から確保される。コンストラクタ 0xA0125D5C が2回連続で 0xA01548D4 を呼び、1個目をジョブ記述子、2個目を request として初期化するのが実読で確認できる（ctor_5d5c.asm）。
- N-044 §2.3 の「alloc クラス 2」という表現の出所は、確保直前に $v0=2 を置く dead な命令列（0xA0125D80 等）とみられ、クラス引数ではない。

### 2.2 ペイロード上限（確度 HIGH・構造から確定）

- request のペイロードは +0x00 からインラインで、制御フィールドが +0x80（INS/センチネル）・+0x84（長）・+0x88（種別）・+0x8C（ctx）に固定されている。したがって **1 request のペイロード（= T=1 の LEN）は最大 0x80 B** で、これを超える構築は制御フィールドを上書きするため構造的にあり得ない。
- 構築関数の実数: 0xA0123210（90 36 系）は +0x84 = データ長+6、0xA0123398（90 38 系）は +0x84 = データ長+0xF を書く。よってデータ部はそれぞれ最大 0x7A B／0x71 B。
- ECM 級（約 0x9E B の APDU 全体）の扱い: カードモジュール内に T=1 チェイニングによる分割は無い。**POD 層（0xA01262CC のタグ 0x85 処理）が状態+0x12C を上限に複数 request へ分割**して順次投入するのが純正の分割規則（§1.3）。90 34（ECM）そのものの構築箇所は CP 側（"Make ECM APDU" 系文字列の側）で、本モジュール範囲では未同定（N-044 §2.6 の記述どおり）。

### 2.3 未同定として残すもの

- プールの**ブロック実サイズ**そのものは分離できなかった。request レイアウトから下限は 0x90 B。ブロックサイズはメモリマネージャ初期化（0xA01524A4 とその呼出し側）が descriptor @phys 0x23F364 へ設定する値で決まるが、本セッションでは当該 descriptor のフィールド初期化まで追い切れていない。次に見るべき場所: 0xA01524A4 の呼出し元と、descriptor +0x04（free 時に obj ポインタから引かれるヘッダオフセット）の設定箇所。Mode Q の設計上は §2.2 の 0x80 B が実効上限であり、ブロック実サイズは実装の前提にならない。

## 3. N-051 NS/NR リセットの同定

census: 状態 +0x110（NS）／+0x114（NR）へのストアはカードモジュール全域で10件のみ（census110.py）。

### 3.1 明示リセット（ゼロクリア）箇所 — 3系統（確度 HIGH）

1. **活性化（コールドリセット）シーケンス内の初期化ブロック ×2実装**:
   - カードリセット関数（MMR 0x1090 の挿入検出、イベント 0x382/0x383 発行、CMD 0x1030 = 0x8400 を書く関数。0xA01257xx–0xA0125D40 の範囲）内の 0xA0125908／0xA012590C。
   - オープナ 0xA0125D5C のインライン活性化シーケンス内の 0xA0125ED4／0xA0125ED8。
   - 両者とも同じ初期化集合: NS=0、NR=0、+0x124=0、+0x128=0、+0x12C=0、+0x148/+0x14C/+0x150/+0x154 = −1、+0x118 の bit1 クリア、ETU 分子を 372 に戻し MMR 0x1020 を再設定、+0x11C = 2（0xA0125D5C 側）。
2. **受信完了パス内のリセット（ステートマシン 0xA0124314）**: 0xA0124A58／0xA0124A5C。条件: 完了した request の種別フィールド（+0x88）が 0x80 で、受信バッファ第2バイト（状態+1）の下位ニブルが 0 のとき NS=0、NR=0 とする。リセット種別ジョブの応答を受けた際のシーケンス初期化と読める（「RESYNC 応答時」という意味づけは推測・MED、コード位置と効果は HIGH）。
3. **ブート時初期化**: POD 初期化関数（≈0xA012B070）が状態構造体全体を memset するため NS/NR も 0（N-044 §4 の再確認）。

### 3.2 リセット以外の NS/NR 書込み（保守経路、確度 HIGH）

- NR: 受信した I ブロックに対し (NR+1)&1 を書く（0xA0124920、ステートマシン）。受信 PCB の bit 0x20（チェイニング）が立つ場合は致命トレース行きで処理されない。
- NS: R/S ブロック応答受信時、完了 request の +0x80 == 0x80 なら NS ← 受信 PCB の bit4（相手の NR）（0xA0124A24）。
- NS: 受信完了ポーラ 0xA0125FE0 内の2件（0xA012607C、0xA01260FC）が I ブロック完了で NS をトグルする（N-044 §2.5 の記述と一致）。

### 3.3 セッション占有と投入の安全性（確度 HIGH）

- 実行は直列: ステートマシン／ポーラが先頭ジョブを1件ずつ処理し、完了で次を取る。処理中に投入されたジョブはリストに並ぶだけで、0xA0121700 は「エンジンが空いていれば即交換開始、忙しければキュー登録のみ（戻り値で判別）」という規約（§1.4）。
- したがって **Mode Q で他ジョブ実行中に投入しても構造的には安全**（割り込みではなく順番待ちになる）。注意点は §1.5 のパージで、活性化失敗等の局面ではキュー内ジョブが所有者通知つきで一括破棄されること。

## 4. N-045 コードケーブ空きの実証

### 4.1 ロードマップ（確度 HIGH）

イメージは単一フラットロードである。ヘッダのベクタ表（+0x110、6エントリ）はセグメント記述子ではなくトランポリン・スニペットで、両ローダ（純正／みこす版）ともイメージ全長 0x126F90 を phys 0x100000 へ一括コピーする（フェーズ1監査 AUDIT.md）。対応は全域 1:1: **file offset F ↔ VA 0xA0100000+F（KSEG1）／0x80100000+F（KSEG0）**。BSS（状態構造体 0x80237FE8 等）はイメージ終端 phys 0x226F90 より上にあり、候補ゼロランはすべてロード範囲の内側にある。よって候補は「リンカ意味での BSS」ではない。問題は実行時に他用途（スタック等）として使われるかどうかに絞られる。

ゼロランの実測（zeroruns.py、イメージ実バイト）: file 0xCB18 長 0x110E8（69,864 B）、file 0x1E238 長 0x19C4（6,596 B）、file 0x1DC5F 長 0x48B（1,163 B）、file 0x1FD10 長 0x401（1,025 B）。設計書の数値と一致。

参照 census（cave_census2.py）: イメージ内ポインタ dword（KSEG0/KSEG1 形式）、jal/j の飛び先、lui/addiu ペアによるアドレス構築、の3方式で候補範囲内への参照を数えた。

### 4.2 候補ごとの判定

**file 0xCB18（69,864 B、VA 0xA010CB18–0xA011DC00）→ rejected（使用中のデータ領域）**
参照 65 件。ブートコードが内部の複数アドレス（0xA010FC00、0xA0110000、0xA0110400、0xA010DC00、0xA010EC00 等）を構築して使う大きな表領域。設計書の「第1候補にしない」は正しく、候補から外す。

**file 0x1DC5F（1,163 B、VA 0xA011DC5F–0xA011E0EA）→ rejected（スタック領域）**
直前（file 0x1DC00–0x1DC5E）にあるトランポリン（ブートテーブル entry から届く）が、`$sp = 0xA011DDE4` または `$sp = 0xA011DF64`（いずれも本ラン内）を設定してから処理へ入る（0xA011DC1C／0xA011DC30 の lui/addiu が census の2ヒット）。本ランはタスクスタックであり、ハンドラを置けばスタックと衝突する。

**file 0x1FD10（1,025 B、VA 0xA011FD10–0xA0120111）→ rejected（ブートテーブルのエントリ／スタック複合領域）**
ブートコード（0xA0108A98–0xA0108C44）がファイル 0x820 域に構築するエントリ表に、チップ variant によらず **0xA011FD10 そのもの**（表 +0x44）と **0x80120100**（表 +0x48、本ラン末尾 file 0x20100）が登録される。前項のトランポリンは実際に `jr 0x80120100` でこのエントリへ飛ぶ。本ランはエントリ／スタック複合領域の一部であり空きではない。

**file 0x1E238（6,596 B、VA 0xA011E238–0xA011FBFC、KSEG0 では 0x8011E238）→ 唯一の生存候補（確度 MED-HIGH）**

- ブートエントリ表（file 0x820 域）の全 variant 分の登録値を列挙しても、本ラン内部を指すエントリは無い（最寄りは variant 0 の 0xA011FC00 = 本ランの終端 +4）。
- ロード範囲内であり BSS ではない（§4.1）。ブートコードの memset 的処理はエントリ表の構築のみで、本ランをゼロ初期化するコードは無い（ゼロはイメージ自体の内容）。
- 位置とサイズの確定: **file 0x1E238–0x1FBFC、6,596 B、VA 0xA011E238（KSEG1）／0x8011E238（KSEG0）**。Mode D ハンドラ（数百バイト〜1KB 超の見積）にもバリアント A の拡張先としても十分な大きさ。
- 残る留保: 本ランはトランポリン／スタック複合領域（file 0x1DC00–0x20111）の内側に位置する。テーブル経由以外の間接参照（計算で求めるアドレス）までは静的に否定しきれない。**最終実証は設計 §8-2 の実機側（純正ブート後に本ランが書き換わっていないかの読み戻し比較）**で、本セッション（静的のみ）の範囲外。静的には「参照される経路は見つからなかった」が正確な表現で、「使われていないことが証明された」ではない。

## 5. Mode Q 仕様の完成度評価

N-044 終了時点で不足とされた5項目の現在地:

| # | 項目 | 現在地 |
|---|---|---|
| 1 | pool の実サイズとペイロード上限 | **解消**（実効分）: 上限は構造的に 0x80 B／request と確定。分割は POD 層が +0x12C 上限で複数 request 化。ブロック実サイズのみ未分離（実装の前提にならない） |
| 2 | 応答データの受け渡し先 | **解消**: 完了コールバック（aux）が状態 RX バッファをその場で解釈し、デスクリプタ（キー 0xC/0xF）または 0xA0121918 経由でチャネル層へ渡す（§1.2） |
| 3 | ctx の実体と流用可能な既存 ctx の特定 | **未解消**: オープナ 0xA012BC70 が作るチャネルオブジェクトの精読がまだ。フック（ワーカー文脈）から使う ctx の選定はハンドラ実装時の残件 |
| 4 | NS/NR リセットとセッション占有時の安全性 | **解消**: リセット箇所を全同定（§3）。投入は直列キューで構造的に安全（§3.3） |
| 5 | 0xA0181FCC／0xA0182708 本体 | **解消**: 両本体を読了（§1.4） |

新たに分かった Mode Q の要点: ハンドラは自前の完了コールバックを aux に渡せる。応答は状態 RX バッファ（+0x130 fill／+0x134 確定長）に残るので、コールバック内（またはポーリング）で読める。投入側の仕様は「request を組む（ペイロード ≤0x80 B、+0x80 = INS または −1、+0x84 = 長、+0x88 = 種別、+0x8C = ctx）→ 0xA0121700（ctx, req, callback）」で完全に具体化した。

**結論: N-047（フック決定実験、設計 §8-4）の前提は揃った。** N-047 自体はテーブル entry の差替え可否の実証であり Mode Q の成否に依存しないが、その先のハンドラ実装に必要な仕様は、残る未確定が「流用する ctx の選定」（項目3）と「ケーブの実機読み戻し実証」（§4.2 の留保）の2点まで減った。どちらも N-047 と並行または直後に処理できる性質のものである。
