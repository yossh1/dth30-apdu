## 0. 仮説と判定（要約）

- 仮説A: ジョブ投入は単一受付口＋キュー経由で、モジュール内にジョブ実行側がある ／棄却条件: 同期直接呼出しのみでキュー構造が無い場合
  → **confirmed（キューは単一リンクリスト）**。受付口は 0xA0121700 に集約され、セッションオブジェクト内のジョブリストへ登録される。実行側はポーリング駆動の巨大ステートマシン 0xA0124314。
- 仮説B: モジュール内にジョブ種別ディスパッチ（Resync/Init/ECM 相当）がある ／棄却条件: 単一直列フローのみの場合
  → **rejected（形を変えて）**。種別ディスパッチは存在しない。代わりに「汎用 T=1 ブロック交換＋ペイロード駆動」というモデルで、ジョブ種別はリクエストオブジェクトの kind フィールド（I/R/S）とペイロード内容（APDU そのもの）の組合せで表現される。単一直列フローでもない（活性化・交換・受信完了が別々のポーリング関数に分かれる）。
- 仮説C: T=1 状態は静的構造体に保持され ATR 処理が初期化する ／棄却条件: ATR 処理から静的構造体への書込みが無い場合
  → **confirmed**。状態構造体は静的配置（VA 0x80237FE8、0x190 B）で、ATR パーサ 0xA0121064 が +0x118/+0x120/+0x124/+0x128 を更新し ETU を MMR 0x1020 へ再設定する。

## 1. 全体モデル

```
[CP タスク 0xA01F7xxx]  ← DDR デスクリプタ＋イベントで通信（§4、境界の内訳は未同定）
        │  （直接の jal はカード層へ届かない。CP からの jal は汎用 0xA0187D90 等のみ）
[POD/CableCARD ライブラリ 0xA0127000–0xA0130000]
        │  リクエストオブジェクトを構築（payload/APDU をインライン格納）
        ▼
[投入 API 0xA0121700 (ctx, request, aux)]   ← 本書で同定した受付口
        │  ジョブ記述子を pool から確保し、セマフォ保護下で
        │  0xA0181FCC によりセッションオブジェクトへ登録
        ▼
[セッションオブジェクト 静的 @0x80240AA0（0xB3C B）: +0x1C = ジョブリスト先頭]
        │
[実行側（ポーリング駆動、2つの入口から呼ばれる）]
  ・0xA0124314 カードサービス/ステートマシン（呼出し元 0xA01BA724 の1箇所）
  ・0xA0125FE0 受信完了ポーラ（呼出し元 0xA01BA62C の1箇所）
        │  活性化（ATR）→ ブロック交換 0xA0121264 → 受信ドレイン → 完了処理
        ▼
[内蔵 ISO7816 UART: MMR 0x1020 ETU / 0x1028 TX / 0x102C RX / 0x1030 CMD / 0x1034 転送数
  ＋ GPIO 0x1084–0x1090（RST 等）]
```

## 2. ジョブ投入 API の規約（課題1）

### 2.1 受付口: 0xA0121700（確度 HIGH）

呼出し元13件、すべて POD ライブラリ／カード層内部（0xA0122E2C、0xA01238F4、0xA0124DD0、0xA0124DF4、0xA0124E1C、0xA01263FC、0xA01265C4、0xA012699C、0xA0127A58、0xA01296F4、0xA0129B5C、0xA012A4BC、0xA012BE6C）。CP タスクからの直接呼出しはない。

引数と動作（関数頭 0xA0121700–0xA01217A4 の実読）:
- $a0 = ctx（チャネル/セッション所有者オブジェクト）→ ジョブ記述子 +0x18 に格納。
- $a1 = リクエストオブジェクト（呼出し側が pool から確保し中身を埋めたもの）→ ジョブ記述子 +0x24 に格納。
- $a2 = aux（補助値、用途未同定）→ ジョブ記述子 +0x2C に格納。
- 先頭で状態構造体 +0x118 の bit1（ATR 解析済みフラグ）を検査し、**未活性化なら $v0=1 を返して何もしない**（カード未準備のときに投入できない）。
- ジョブ記述子を pool（global 0x8023709C = $gp-0x6BC4、alloc 0xA01548D4）から確保し、+0x0C=0x100（種別タグ）、+0x10=0、+0x14=−1、+0x28/+0x30/+0x34/+0x38/+0x3C=0 で初期化。
- セマフォ（ハンドル global 0x802371B8 = $gp-0x6AA8、wait 0xA01E5C54／post 0xA01E60E4）で保護して 0xA0181FCC（セッションオブジェクト, ジョブ）を呼び登録する。

### 2.2 ジョブ記述子（pool 確保、確度 HIGH）

| offset | 内容 |
|---|---|
| +0x0C | 種別タグ = 0x100（投入 API・コンストラクタ 0xA0125D5C とも同値） |
| +0x10 | 0（未同定） |
| +0x14 | −1 初期値（未同定、完了コード格納先の候補） |
| +0x18 | ctx ポインタ（0xA0121700 経由の場合。コンストラクタ 0xA0125D5C では 0） |
| +0x24 | リクエストオブジェクトへのポインタ |
| +0x2C | aux（0xA0121700 の $a2） |
| +0x28, +0x30–+0x3C | 0 初期化（未同定） |

キュー表現: セッションオブジェクト（静的 @0x80240AA0、初期化時に 0xB3C B を memset）の **+0x1C がジョブリスト先頭ポインタ**。登録は 0xA0181FCC、取外し/次要素取得は 0xA0182708（セッション, ジョブ）→ $v0 = 次ジョブ。リングバッファではなくリンクリスト（確度 MED-HIGH: 0xA0182708 の呼出しパターンと戻り値の使い方からの推定。本体は未読）。

### 2.3 リクエストオブジェクト（pool 確保、alloc クラス 2、確度 HIGH）

呼出し側（POD ライブラリ等）が構築する。コンストラクタ例: 0xA0125D5C（オープナ経由の投入。+0x80=−1、+0x84=0、+0x8C=ctx を設定）。

| offset | 内容 | 根拠 |
|---|---|---|
| +0x00.. | **送信ペイロード（インライン）**。交換関数が $fp+index で直接読む | 0xA012141C/0xA0121540 の TX ループ |
| +0x80 | S ブロックのコードバイト／兼「未処理センチネル」。構築時は −1。交換時は S 種別のとき PCB = 本値 \| 0xC0。状態機械は −1 の間「活性化が先」と解釈 | 0xA0121264 頭、0xA0124314/0xA0124D50 の分岐 |
| +0x84 | ペイロード長（= T=1 の LEN）。転送総数・期待受信数とも本値+4 で計算 | 0xA0121478（CMD 0x1030 値）、0xA0126038 付近 |
| +0x88 | **ブロック種別: 0=I ブロック / 1=R ブロック / 2=S ブロック** | 0xA0121264 の3分岐（後述） |
| +0x8C | ctx ポインタ（活性化通知 0xA0123F08 の宛先） | 0xA01243BC、0xA0124D6C |

注意（未解決）: ペイロードが +0x00 からインラインで、制御フィールドが +0x80 にあるため、**1 回の交換で送れるペイロードは最大でも 0x80 B 程度**と読める。ECM APDU（90 34、データ約 0x9E B）をどう分割/処理するかは未同定（§7 の残件）。alloc クラス 2 の実サイズも未同定。

### 2.4 交換関数 0xA0121264（確度 HIGH）

呼出し元6件（0xA01217B0、0xA01246CC、0xA0124AC0、0xA0124C20、0xA0124E90、0xA0126208）、大半はステートマシン内部。$a0 = ジョブ記述子、内部で req = *(job+0x24) を取る。

- ヘッダ3バイト（NAD=0、PCB、LEN=req+0x84）を組立て、PCB は req+0x88 で分岐:
  - 0（I）: PCB = 状態+0x110（NS）<< 6
  - 1（R）: PCB = 状態+0x114（NR）<< 4 | 0x80
  - 2（S）: PCB = req+0x80 | 0xC0
- ペイロードを MMR 0x1028（TX FIFO）へ送出（同時に固定ログバッファ 0x8023F450 へコピー）。LRC はヘルパ 0xA0121224。
- MMR 0x1030 へ (len+4)<<16 | 0x8001 を書いて転送開始。FIFO ドレインを 0x1034 ポーリングで待ちつつ残りを送る（ウォッチドッグポーク 0x0B57AC1E → 0xA0100540 を含む）。
- 送信開始時に MMR 0x6130/0x6134（タイマ）→ 状態 +0x108/+0x10C に記録。

### 2.5 実行側ステートマシン 0xA0124314（確度 HIGH）

単一の巨大関数（0xA0124314–0xA01253FC、約4.3KB、プロローグ/エピローグ各1つを確認）。ポーリングで次を進める:

1. 活性化フェーズ: 状態+0x118 & 3 == 1 かつ 状態+0x108 からの経過 ≥ 0x7D1 のとき、リスト先頭ジョブを見る。req+0x80 == −1 なら活性化が必要:
   - 状態+0x188（リトライカウンタ）< 2 の間: 0xA0123F08（req+0x8C, 1）で所有者へ通知し、セマフォ保護下でジョブを取外し（0xA0182708）、ジョブと req を解放（free 0xA0154C9C）、状態+0x11C/+0x130 をクリア。
   - カウンタ ≥ 2 で実 ATR シーケンスをインライン実行: RST ピン（0x1088 に 0x3000 セット→ポーリング→クリア）、CMD 0x1030 = 0x8100（ATR 受信）、RX ドレイン（0x102C を最大 0x40 回）、時刻を状態+0x108/+0x10C へ。
2. 交換フェーズ（状態+0x11C ∈ {1,2}）: ジョブを順に取外し・解放しながら、対象ジョブについて 0xA0121264 を呼ぶ。受信バイトは状態構造体の RX バッファ（+0x00 起点、fill カウンタ +0x130）へ蓄積。
3. ATR 完了フェーズ: 先頭バイトが 0x3B/0x3F（TS バイト）であることを確認し、req+0x80 == −1 のジョブについて **ATR パーサ 0xA0121064（$a0 = 状態+0x130 = ATR 長）** を呼び、結果を 0xA0123F08（req+0x8C, 結果）で所有者へ通知。成功時は pool オブジェクト3個を構築（0xA0121EB4/0xA0121EC8/0xA0122130）し 0xA0121700（req+0x8C, obj, 0）で後続ジョブとして投入する（セッション確立後の内部ジョブ連鎖）。
4. タイムアウト監視: 状態+0x138 ≠ 0 かつ +0x140/+0x144 からの経過 ≥ 0x1389 で 0xA0123464（*(0x80255158), 0）を呼ぶ（詳細未読）。

受信完了ポーラ 0xA0125FE0（呼出し元 0xA01BA62C）: MMR 0x1094 の bit 0x100（受信完了割込み）をポーリングしクリア。状態+0x11C == 1 のとき受信数（0x1034 & 0x7F）と req+0x84+4 を照合し、不足分を RX FIFO から状態バッファへ補充。I ブロック（req+0x88 == 0）完了で **状態+0x110（NS）を (x+1)&1 でトグル**。

### 2.6 ジョブ種別の表現（課題1の後半、確度 HIGH）

純正には Resync/IFS/Init/ECM の「ジョブ種別コード」は**存在しない**（モジュール全域の呼出し・分岐を追った範囲で、種別列挙によるディスパッチは見つからなかった。「存在しない」の根拠: 投入 API が汎用1本であり、交換関数の分岐は T=1 ブロック種別のみで完結していること）。
対応づけは次のとおり:
- S-RESYNC / S-IFS: req+0x88 = 2（S ブロック）、req+0x80 = S コード（PCB = コード|0xC0）。
- INITIAL_SETTING（90 30）/ ECM（90 34）等の APDU: req+0x88 = 0（I ブロック）、ペイロード = APDU バイト列そのもの（CP/POD 側で組立て。CP 内に "Make ECM APDU" 系文字列あり）。

## 3. 完了通知の経路（課題2）

- **コールバックはない**（確度 MED-HIGH: 投入 API・ステートマシン・交換関数のいずれにも ctx 経由の関数ポインタ呼出しが見当たらない）。
  - 【訂正 2026-11-23】上記は誤り。完了コールバックは存在し、投入 API の第3引数 aux（= ジョブ記述子 +0x2C）が状態機械 0xA01248AC の jalr で呼ばれる。詳細は N049-051-DESK.md §0／§1.2 を参照（原文は経緯として残す）。
- ジョブ完了 = ステートマシンがジョブをリストから取外し（0xA0182708）、**ジョブ記述子とリクエストオブジェクトを pool へ解放**する。投入側はポインタを保持して完了を待つ設計ではない。
- 所有者への能動通知は **0xA0123F08（ctx, コード）**（確度 MED）: ctx+0x18/+0x1C の2ワードと ctx+0x378 域のフィールドを、検索関数 0xA0153A38（キー 0xF）で得た DDR デスクリプタへ未整列ストアで書き戻す。呼出し箇所: 活性化要求時（コード=1、0xA01243BC/0xA01245C8/0xA0124680）、ATR 解析後（コード=解析結果、0xA0124D74）。→ **CP/POD との境界は DDR デスクリプタ＋この書戻し**が本命。
- イベントプリミティブ 0xA01E6680/0xA01E6620 がカードイベント ID **0x3C2 / 0x3C3** で使われる（0xA0124CF8–0xA0124D48: ATR 受信完了時に 状態+0x134 ← 状態+0x130（受信長を確定）してから発行）。オープナ側ではチャネル別 ID (chan<<2)+0x341 の同プリミティブ使用あり。post/read のどちらがどちらかは未確定（確度 MED）。
- 応答データの所在: 受信バイトは状態構造体 RX バッファ（+0x00 起点）に貯まり、確定長は +0x134。**ただし投入側（POD/CP）のバッファへ誰がコピーするかは未同定**（候補: 0xA0123F08 の書戻し、または POD 側が 0xA01262CC 等で状態構造体を直接読む。0xA01262CC は先頭バイト 0x84 のバッファを状態+0x148/+0x14C と照合する処理で、受信後処理の一部と見られる）。

## 4. T=1 状態変数（課題3、確度 HIGH）

- **状態構造体: 静的配置 VA 0x80237FE8（phys 0x237FE8）、サイズ 0x190 B**。ポインタ global は 0x802370E0（$gp-0x6B80）に格納され、モジュール全域がこの global 経由で参照する。
- 初期化者: POD ライブラリ域の初期化関数（入口 ≈0xA012B070、呼出し元は未同定）。memset（0x190）後、UART を初期設定: ETU 分子 372 を +0x120 に入れ MMR 0x1020 へ書込み、0x1024 = 0xBBF、0x1080 へクロック分周値、0x1084/0x1088 へピン設定、MMR 0x109C の値を +0x184 に保存、0xA012B3F8(1) の戻りを +0x180 に保存。同関数はセッションオブジェクト（@0x80240AA0、0xB3C B）も memset し 0xA018361C（obj, 0xD, 1）で登録する。
- ATR パーサ 0xA0121064（呼出し元は 0xA0124D64 の1件のみ）: RX バッファ（+0x00 起点、TS=+0、T0=+1…）を解析し、+0x118 に bit1 をセット、+0x120 = ETU 分子（372 または 744）、+0x124 = 除数/プロトコル値、+0x128 に解析バイトを保存、ETU を再計算して MMR 0x1020 へ書く（0xA0121214）。
- フィールド表（判明分）:

| offset | 内容 |
|---|---|
| +0x000–0x0FF | RX ワークバッファ（ATR・応答がここに貯まる） |
| +0x100/+0x104 | 時刻（活性化開始、64bit タイマ値） |
| +0x108/+0x10C | 時刻（最終交換開始） |
| +0x110 | **NS**（I ブロック送信シーケンス、1bit。受信完了でトグル） |
| +0x114 | **NR**（受信シーケンス、1bit。R ブロック PCB 生成に使用） |
| +0x118 | フラグ（bit0: 活性化要求/済の表示に使用、bit1: ATR 解析済み） |
| +0x11C | フェーズコード（0=待機、1=交換中、2=ATR/交換フェーズ） |
| +0x120 | ETU 分子（372/744） |
| +0x124 | ETU 除数／プロトコル値（ATR 由来） |
| +0x128 | ATR 解析で保存されるバイト（TAi 相当、未確定） |
| +0x130 | RX fill カウンタ |
| +0x134 | RX 確定長（完了時に +0x130 からコピー） |
| +0x138, +0x140/+0x144 | タイムアウト監視用（閾値 0x1389） |
| +0x148/+0x14C | 受信データと照合される ID 系値（0xA01262CC が参照。INITIAL_SETTING 応答由来の候補） |
| +0x180 | 初期化時の値（0xA012B3F8(1) の戻り） |
| +0x184 | 初期化時の MMR 0x109C スナップショット |
| +0x188 | 活性化リトライカウンタ |

- セッション開始/終了の初期化: 開始 = 上記初期化関数（ブート時1回）＋ ATR パーサ（接続毎）。フェーズ開始時にステートマシンが +0x100/+0x104 と +0x130 をゼロクリアする（0xA01246E0、0xA0124C34）。**NS/NR（+0x110/+0x114）の明示リセット箇所は未同定**（活性化経路の未読部か 0xA0124210〈検証/準備関数、呼出し元2件〉の候補）。

## 5. みこす card.rs との対応（課題4）

`cfw-audit/driver/crates/dth30-fw/src/card.rs` のジョブモデル（Resync/Ifs/Init/Ecm）との対応:

| みこすのモデル | 純正の対応物 | 備考 |
|---|---|---|
| Job::Resync（S-RESYNC） | req+0x88=2（S）、req+0x80=S コード（RESYNC） | PCB 生成規則（コード\|0xC0）が一致 |
| Job::Ifs（S-IFS） | req+0x88=2（S）、req+0x80=S コード（IFS）、ペイロードに IFS 値 | 同上 |
| Job::Init（INITIAL_SETTING 90 30） | req+0x88=0（I）、ペイロード=APDU 全体 | 純正に専用分岐なし |
| Job::Ecm（90 34） | req+0x88=0（I）、ペイロード=APDU 全体 | 同上。分割方法は純正側未同定 |
| T=1 状態（NS/NR、ETU） | 状態構造体 +0x110/+0x114、+0x120/+0x124 | 保持場所は静的構造体（彼の実装ではモジュール内状態） |

評価: 彼の4種別モデルは、純正の「汎用ブロック交換（kind 3種）＋APDU ペイロード」という実構造を、用途側から切り直したものとして**矛盾なく対応する**。純正側に種別ディスパッチが無いことは、彼のモデルが「純正の写し」ではなく「等価な再実装」であることを示す（同定の裏付けとしては、PCB 生成・S ブロック扱い・NS トグルの一致が根拠になる）。

## 6. Mode Q 実装仕様の具体化評価

APDU-DESIGN.md の Mode Q（純正カード層のジョブ投入に相乗り）について、ハンドラがジョブを組み立てるのに必要な情報:

**揃ったもの（今回確定）**
- 投入 API の入口・引数・前提条件: 0xA0121700（ctx, request, aux）。ただし ATR 解析済み（状態+0x118 bit1）でないと受理されない。
- リクエストオブジェクトのレイアウト（payload インライン +0x00、+0x80=−1 初期化、+0x84=長、+0x88=種別、+0x8C=ctx）とジョブ記述子の自動構築（API 側）。
- 実行がポーリング駆動（0xA0124314/0xA0125FE0）で、投入は「登録して後は状態機械が処理する」非同期モデルであること。フック側は投入後に自力で完了を検出する必要がある。
- T=1 状態の所在（0x80237FE8）と主要フィールド。Mode D の前提（状態の読み取り・セッション競合の判断材料）もここから取れる。

**不足（次に同定が要るもの）**
1. pool alloc クラス 2 の実サイズと、ペイロード上限（0x80 B で収まるか、ECM 級 APDU の分割規則）。→ alloc 0xA01548D4 のクラス表を読む。
2. 応答データの最終的な受け渡し先（状態 RX バッファから POD/CP へ誰がコピーするか）。Mode Q で自前 APDU の応答を読むにはここが必須。→ 0xA0123F08 本体の精読と 0xA01262CC 以降の POD 受信処理。
3. ctx の実体（POD チャネルオブジェクト）の生成経路と、フック側が流用できる既存 ctx の特定。→ オープナ 0xA012BC70 が作るチャネルオブジェクト（+0x64→サブオブジェクト）の精読。
   【訂正（2026-11-23）】本項目の前提「0xA012BC70 はチャネルオブジェクトのオープナである」は H-063 として棄却済み（実体は関数 0xA012B7C8 の共有リターンブロックでエントリではなく、「+0x64→サブオブジェクト」の読みも再現できなかった）。ctx の特定は N-052 で別経路（アンカ 0x80255158 のリスト内の +0x30 bit 0x10 ノード）により解消済み。根拠: cfw-audit/N052-N046-DESK.md §1.1。
4. NS/NR のリセット箇所と、セッション占有の判定方法（他ジョブ実行中に投入するとリストへ並ぶだけで安全か、の確認）。→ 0xA0124210 の精読。
5. 0xA0181FCC/0xA0182708 本体（リスト操作の正確な意味、優先度や割込みの有無）。

結論: **Mode Q の「投入側」の仕様は実装可能な水準まで具体化した。「応答の回収側」が残りの本体**であり、上記2が埋まれば設計 §8 の N-047（フック決定実験）の前提がほぼ揃う。
