# H-054 棄却条件（起草 — 調査員、2026-11-23 机上）

対象仮説 **H-054**: 「Func 0x04 のテーブル entry（file 0xFF3A0）を既存ハンドラへ
差し替えるだけで、ファーム側に新しい RPCI コマンドを追加できる」。
本書は検証係の申し送り（N-047 実施前に調査員が棄却条件を明示する）に応じた
起草であり、台帳への登録は記録係が行う。N-047／N-053 の実施前に本書の条件を
台帳へ登録すること。

## 0. 判定の物差し（ベースライン）

すべての比較は、2026-11-22 の A/B/A 実験で得た純正イメージの実測値を
ベースラインとする:

- 起動ハンドシェイク: MMR 0x3028 が 5 → ACK → 0 と遷移する。
- TS: 10 秒取得で 21.5〜21.9 MB、同期率 100%。
- 改変の着地確認: 対象バイト／dword が DDR 上で改変値どおりに読み戻せる。

## 1. N-047（フック決定実験）に対する棄却条件

実験の形: テーブル entry（file 0xFF3A0）の dword だけを
0x80153550 → 0x8015361C（既存の固定応答 "5" ケース）へ差し替えたイメージを
Stage A リプレイで投入し、Func 0x04 を発行して固定応答が返るかを見る。
この改変は 4 バイト（1 dword）であり、N-048（複数バイト改変の実績）の
最初の記録を兼ねる。

- **条件 R1（差し替えが効かない → 棄却）**: 改変 dword の DDR 着地が
  読み戻しで確認できるのに、Func 0x04 を発行しても固定応答ケース相当の
  応答が得られない（MMR 0x3028 が 5 にならない、または応答自体が返らない）
  ことが、純正イメージでの対照（既存 Func の発行・応答が正常）と比較して
  再現する。→ 「Func はテーブル entry 経由でディスパッチされる」という
  前提が崩れるため **H-054 を棄却**する。
- **条件 R2（通常動作が壊れる → 棄却）**: 改変イメージで通常動作スポット
  （起動ハンドシェイク、Func 0x08 による選局、TS 同期率）のいずれかが
  §0 のベースラインから劣化する。→ 4 バイト改変でも副作用があることになり、
  「entry 差し替えだけ」という形の **H-054 は棄却**する（改変方式自体の
  見直しが要る）。
- **条件 R3（到達不能 → 原則棄却、ただし手順監査を先行）**: Func 0x04 が
  ワーカーへ届かない事象が改変側特有に再現する場合は到達不能として
  **H-054 を棄却**する。ただし、自前発行手順（hw22 系 Stage A リプレイ）の
  忠実度と切り分けが付かない場合は棄却せず「判定保留・手順監査へ差し戻し」
  とする（ACK≠効果／自分の再現を先に疑う、の原則）。
- **条件 R4（複数バイト改変への条件）**: 改変イメージ自体が着地しない
  （DDR 読み戻しで改変 dword が一致しない）場合は、それだけでは棄却しない。
  先に 1 バイト改変イメージで同じ手順が着地することを再確認してロード手順を
  監査し、手順が健全なのに 4 バイト版だけ着地しないことが再現したら、
  「1 バイトを超える改変に対する検証の存在」を疑い **H-054 を棄却**する。

成功条件（参考）: 着地確認済み＋Func 0x04 で固定応答 "5" 相当が観測でき、
通常動作スポットがベースラインどおり → H-054 は confirmed へ進み、
N-048 は「4 バイト改変の着地・実行」の正の記録を得る。

## 2. N-053（ケーブ実機実証）に対する線引き

対象: 候補ケーブ file 0x1E238（6,596 B、VA 0xA011E238）。実験の形:
同領域へ既知パターンを書いたイメージを投入し、起動後に DDR を読み戻して
パターンと比較する。あわせて純正イメージでの同アドレス（0 であること）と
通常動作を確認する。

- **C1（使用可）**: 読み戻しがパターンと一致し、純正では同アドレスが 0 で、
  通常動作がベースラインどおり → ケーブ使用可。H-061 は confirmed へ。
- **C2（ケーブ前提の棄却・H-054 は棄却しない）**: 読み戻しがパターンと
  一致しない（0 のまま、または別データ）→ その領域はロード対象外か
  起動過程で上書きされている。→ 「file 0x1E238 をケーブとする」前提は
  棄却するが、**H-054 自体は棄却せず §3 の縮退判定へ進む**。
- **C3（ケーブ前提の棄却・同上）**: パターンは着地するが通常動作が
  ベースラインから劣化する → 領域が実行時に使われている。→ C2 と同じ扱い。
- **C4（部分的成立）**: 領域の途中までパターンが一致し、途中から別データに
  なる場合は、一致した範囲を使用可能サイズとして実測し、その範囲で
  再判定する（棄却ではない）。

## 3. 縮退の線引き（ケーブが使えない場合）

- **スタブ内蔵版への縮退（H-054 は継続）**: ハンドラ本体が Func 0x04 スタブ
  本体の 0xCC バイトに収まるなら、ケーブなしでも Mode Q の最小実装
  （ジョブ投入＋完了コールバックでの応答コピーアウト）が可能であり、
  その場合は H-054 を棄却せず「スタブ内蔵版」として継続判定する。
  収まるかの判断は、実装着手時にハンドラの命令数を実測して行う。
- **Mode D 単独への縮退はしない**: Mode D（セッション非アクティブ時に
  ハンドラが T=1 を直接駆動）は必要コード量が大きく、0xCC バイトに
  収まらない見込みが高い（推測）。ケーブ喪失時に Mode D 単独へは縮退せず、
  代替ケーブの再 census（他のゼロ参照領域、既存コードの dead 領域の再評価）
  を先に尽くす。
- **最終棄却**: 代替ケーブの再 census でも使用可能な領域が得られず、
  かつハンドラが 0xCC バイトに収まらないことが実測で確定したら、
  置き場所がないため **H-054 を棄却**する（設計自体は APDU-DESIGN.md に
  残し、将来の別経路に委ねる）。
