## 1. 診断（確定した機構）

### 1.1 一次情報で確認した vpcd／vicc の在席設計

vsmartcard 3.3+dfsg-2（Debian の vicc 0.8）のソースで確認:

- 在席判定は `vicc_present()` = 「vicc に接続でき、CTRL_ATR への応答が1バイト以上あること」。ATR 応答が **0 バイトなら `vicc_eject()` で接続を切る**設計で、在席は本質的に「接続 ⇔ カードあり」で表すのが上流の想定。
- `vicc_transmit()` は `io_lock`（pthread mutex）を保持したまま応答待ちに入る。存在確認も送信も同じロックで直列化される。
- vicc 側 `VirtualICC.run()` は単一スレッドで、CTRL_ATR には `os.getATR()` の戻りをそのまま送る。長さの検査はない。

### 1.2 詰まりの機構（ラボ再現＋スレッド状態で確定）

旧版橋渡しは不在時に `getATR() → b""` を返し、vicc が **長さ0のフレーム `[00 00]`** を送っていた。これを受けた vpcd の `recvFromVICC()` は、ペイロード長 0 に対して `recvall(sock, buf, 0)` = `recv(fd, NULL, 0, MSG_WAITALL|MSG_NOSIGNAL)` を実行する。**この長さ0・MSG_WAITALL 付き recv は即座に返らず、後続データが来るまでブロックする**（Linux ストリームソケット上の実測事実）。

ラボ（スロット 00 01、フレーム記録プロキシ＋スタブ serve）で旧版を再現し、詰まった瞬間の状態を採取した:

- フレーム会計は完全一致: ATR 要求80／応答80（13バイト×79、0バイト×1）、APDU 要求86／応答86。未応答の要求は存在しない（要求総数169−応答166=3 は応答不要の電源系制御 ON×2・OFF×1）。**vicc は全てに答え終わって次の要求待ち、vpcd は応答を受け取ったはずなのに進めない**、という状態が再現した。
- pcscd のリーダーイベントスレッドが **fd 10（スロット1の vicc 接続）に対する len=0・flags=0x4100（MSG_WAITALL|MSG_NOSIGNAL）の recv で停止**（`/proc/<pid>/task/*/syscall` で採取）。これが §1.2 の長さ0 recv そのもの。（注記: この採取はラボ再現中にその場で読み取って転記したのみで、生記録はファイルに残されていない。対象プロセスの終了とともに消失済み。機構の裏付けは artifacts 内のフレーム会計と monitor／proxy ログで独立に再現可能。）
- 後続の Transmit 用スレッド2本は同一 futex（io_lock）待ち。**存在確認スレッドが io_lock を握ったまま長さ0 recv で止まるため、リーダー全体が凍る**。
- 新規クライアントの SCardGetStatusChange は「PRESENT のまま・旧 ATR 13バイト」を返し続け、REMOVED は永久に発火しない。モニタの送信ループは #86 で凍結。

N-069 本番インシデントとの対応: serve ジャーナル conn 701（07:49:42.862 UTC の `apdu query`、status 0x00）が存在確認ポーリングの getATR で、橋渡しは空 ATR を返して vpcd 側が長さ0 recv で停止。以後 vicc が serve に一切触れていない（ジャーナル沈黙）こと、#187 が serve に到達していない（io_lock の futex 待ちでフレーム自体が送られていない）こと、再起動まで復旧しなかったこと、すべてがこの機構で説明できる。

### 1.3 棄却した仮説

- **vicc の部分読み取り（partial read）脆弱性**: `__recvFromVPICC` は単発 recv で部分フレームに弱いが、インシデントのジャーナルに "Expected bytes" 警告はなく、ラボのフレーム会計も完全一致したため、本件の原因ではない。
- **橋渡しのクラッシュ／再起動ループ**: インシデント中 vicc プロセスは生存し続け、ジャーナルは沈黙していただけ（落ちていない）。
- **serve 側の未応答**: serve は全要求に応答していた（conn 699/701 が証拠）。詰まりは serve より PC/SC 側（vpcd 内）にある。
- **busy 再試行の暴走（最悪 ≈390 秒）**: 旧版 execute の理論上の上限は確かに長すぎたが、#187 は serve に到達すらしていないため本件の主因ではない。ただし有界化は今回あわせて実施した（§2.3）。

## 2. 修正内容

修正版 `dth_vicc.py`（本番 md5 `03eb5f27…`、修正前 `4ad0bb97…` は 検証ホスト に `.bak-20261123prefix`、ここに `dth_vicc.py.pre-fix` を保存）。

### 2.1 在席は「接続の生死」で伝える（スーパーバイザ方式）

- メインスレッドの監視ループが `apdu query` を 1 秒間隔で叩き、カード状態を能動的に把握する。
- **vpcd 接続はカードが在席かつアクティブな間だけ存在する**（接続ワーカースレッドが VirtualICC を保持）。不在が **8 回連続（約8秒）** 確定したら接続ソケットを shutdown して切断する → vpcd が eject 経路に入り pcscd が REMOVED を出す。再在席で再接続 → INSERTED。
- 猶予 8 秒の根拠: serve が保留 APDU に完了コード 1（→ SW 6985）を返す最遅実測 5.13 秒（N-069 の #186）より長く取ることで、「抜去に跨った Transmit は 6985 で返る」という良い振る舞いを切断より先に完了させる。フレームのちらつき（再活性化中の一時的な 0x00）で切断しない効果もある。
- **query のエラー（serve 停止・ソケット障害）は「不明」として数えない**。serve 障害を抜去と誤認して切断することはない（§3.3・§4.3 で実測）。

### 2.2 空フレームを二度と送らない

- `getATR()` は不在時でも `b""` を返さない。猶予期間中は最後に得た実 ATR を返し続け（切断こそが不在の合図であり、ATR の中身は変えない）、実 ATR を一度も得ていない状態で不在に当たった場合は例外 `CardAbsent` で接続自体を落とす（run() を巻き戻してソケットを閉じる）。

### 2.3 execute() の有界化

- 全体の締切 **30 秒**（busy 再試行込み）。各試行のソケットタイムアウトは残り時間で頭打ち。
- `OSError` 以外の例外も含め **いかなる例外も外に出さない**（最終防衛で捕捉して SW 6F00）。VirtualICC.run() には execute 周りの例外ガードがなく、例外=接続死に直結するため。
- 既存の振る舞いは不変: 61xx/6Cxx 素通し、reason→SW 写像（3→6700、1→6985、2 は busy 再試行、それ以外 6F00）、電源／リセット no-op、ATR・応答の生バイトをログに出さない方針。

## 5. 次段（抜き差し確認）の準備状態

本番は修正版で稼働中（dth-serve／dth-vicc／pcscd／mirakurun すべて active、PC/SC・GR27 とも正常確認済み）。ユーザーの合図でカードを抜いた場合の期待挙動:

1. 抜去に跨った Transmit は serve の完了コード 1 → **SW 6985**（最遅 ~5.1 秒）で返る。
2. 抜去から **約8–9 秒**で橋渡しが接続を切り、PC/SC に **REMOVED** が出る。以後の接続試行は即 NoCard で失敗する（無期限ブロックはしない）。
